# 고객센터 문의 API 계약 제안

마이페이지의 고객센터 팝업은 아래 계약을 기준으로 구현되어 있다. 백엔드가 이 엔드포인트를 제공하면 프런트 변경 없이 문의가 접수된다.

## 요청

- `POST /api/v1/support-inquiries`
- 인증: `Authorization: Bearer {accessToken}`
- `Content-Type: application/json`

```json
{
  "category": "SERVICE",
  "content": "검색한 가챠가 다른 매장에 표시됩니다. 확인 부탁드립니다."
}
```

`category`는 다음 값만 허용한다.

- `SERVICE`: 서비스 이용 문의
- `BUG`: 오류 신고
- `DATA`: 매장·가챠 정보 제보
- `OTHER`: 기타 의견

`content`는 공백을 제거한 뒤 10자 이상 1,000자 이하로 검증한다.

## 응답 예시

```json
{
  "code": "C001",
  "message": "문의가 접수되었습니다.",
  "data": {
    "inquiryId": 1
  }
}
```

## 권장 서버 구조

1. 인증 토큰에서 회원 ID를 식별한다.
2. 문의 유형, 본문, 회원 ID, 접수 시각, 처리 상태를 데이터베이스에 먼저 저장한다.
3. 저장에 성공하면 `201 Created`를 응답한다.
4. 별도 비동기 작업이 팀 공용 메일 또는 Slack 채널로 알림을 전송한다.
5. 알림 전송이 실패해도 저장된 문의는 유실되지 않게 재시도한다.

프런트에서 SMTP·메일 API 키를 보관하거나 메일 서비스로 직접 전송하지 않는다. 서버에서는 HTML을 제거하고 길이 제한, 사용자별 요청 횟수 제한, 중복 요청 방지, 운영자 접근 권한과 감사 로그를 적용한다.

문의 답변이 필요하다면 소셜 로그인 이메일을 자동으로 가정하지 말고, 별도 회신 이메일을 선택적으로 받는 계약과 수집·보유기간을 먼저 합의한다. 현재 프런트는 회신 이메일을 수집하지 않는다.

## 운영 전 확인

- 팀 공용 문의 이메일 또는 Slack 목적지를 확정한다.
- 문의 보유기간과 삭제 절차를 개인정보처리방침에 확정한다.
- 문의 상태(`RECEIVED`, `IN_PROGRESS`, `RESOLVED`)와 운영자 조회 도구를 결정한다.
- 민감정보 탐지 또는 운영자 마스킹 정책을 결정한다.

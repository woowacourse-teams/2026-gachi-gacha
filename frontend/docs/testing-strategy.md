# 가치가챠 프론트엔드 테스트 전략

이 문서는 기능 추가와 리팩터링 이후에도 검색, 지도, 인증, 매장 상세와 마이페이지의 기존 동작이 유지되는지 배포 전에 빠르게 확인하기 위한 팀 기준이다. 도구 설치 자체보다 **사용자가 겪는 중요한 실패를 적절한 계층에서 검증하는 것**을 우선한다.

## 1. 현재 상태와 목표

현재 프론트엔드는 ESLint, Prettier, TypeScript 타입 검사, Jest 단위·통합 테스트, 프로덕션 빌드와 Storybook을 사용한다. MSW는 통합 테스트와 Storybook에서 외부 API 경계를 제어한다. 프론트엔드 변경 PR에는 `Frontend Quality` 워크플로가 정적 검사, 테스트와 두 종류의 빌드를 실행하며, E2E와 시각적 회귀 자동화는 후속 단계로 남겨 둔다. 배포 워크플로는 PR 검증과 분리해 self-hosted runner에서 배포 역할만 담당한다.

테스트 도입의 목표는 다음과 같다.

1. PR에서 주요 회귀를 배포 전에 발견한다.
2. 실패했을 때 원인과 재현 단서를 빠르게 찾는다.
3. 구현 상세를 바꾸는 리팩터링 때문에 테스트를 대량 수정하지 않는다.
4. 느리고 불안정한 테스트를 최소화해 팀원이 자주 실행하게 만든다.

테스트 개수나 전체 커버리지 수치만을 목표로 삼지 않는다. 위험도가 높은 사용자 흐름의 성공·실패·빈 상태가 실제로 보호되는지를 우선한다.

## 2. 기본 원칙

- 컴포넌트의 state, 내부 함수, CSS 클래스가 아니라 사용자가 보고 조작하는 결과를 검증한다.
- 요소는 가능한 한 접근 가능한 역할과 이름으로 찾는다. `data-testid`는 지도 캔버스처럼 의미 있는 역할을 부여하기 어려울 때만 사용한다.
- 네트워크는 `fetch` 자체를 모킹하지 않고 MSW에서 성공, 빈 결과, 오류, 지연 응답을 표현한다.
- 외부 경계인 카카오 지도 SDK, 브라우저 위치 API, PostHog, 소셜 OAuth 제공자는 테스트 대역으로 격리한다.
- 구현을 그대로 복제한 예상값을 만들지 않는다. 요구사항에서 기대 결과를 작성한다.
- 버그를 수정할 때는 재현 가능한 가장 낮은 계층에 회귀 테스트를 먼저 또는 함께 추가한다.
- 테스트끼리 상태, 실행 순서, 로그인 세션을 공유하지 않는다.
- 큰 DOM 스냅샷은 기본 전략으로 사용하지 않는다. 동작은 명시적 단언으로, 모양은 시각적 테스트로 확인한다.

## 3. 테스트 계층과 도구

| 계층          | 책임                                                        | 제안 도구                                           | 실행 시점                                   |
| ------------- | ----------------------------------------------------------- | --------------------------------------------------- | ------------------------------------------- |
| 정적 검사     | 문법, 타입, 포맷, 번들 생성 가능 여부                       | ESLint, Prettier, TypeScript, Webpack               | 로컬, 모든 PR                               |
| 단위 테스트   | 파서, URL 생성, 토큰·라우팅 유틸처럼 입출력이 분명한 로직   | Jest                                                | 로컬, 모든 PR                               |
| 통합 테스트   | 컴포넌트·훅·Context·API 경계를 묶은 사용자 행동과 화면 상태 | Jest, React Testing Library, user-event, MSW, jsdom | 로컬, 모든 PR                               |
| 컴포넌트 상태 | 재사용 UI의 기본·로딩·오류·빈 상태와 접근성                 | Storybook, Story의 `play` 함수                      | 개발 중, 모든 PR                            |
| E2E 스모크    | 실제 브라우저의 라우팅, 반응형 전환, 핵심 사용자 여정       | Playwright                                          | PR의 핵심 Chromium, 릴리스 전 다중 브라우저 |
| 시각적 회귀   | 레이아웃, 간격, 색상, 뷰포트별 깨짐                         | Storybook 기반 시각 비교 도구                       | 기반 도입 후 UI 변경 PR                     |

### 도구 선택 이유

- **Jest**는 팀이 익숙한 테스트 실행기이며 단위·통합 테스트의 실행, 격리, 모킹과 리포트를 한곳에서 관리한다. 현재 Webpack 빌드와는 별도로 Babel 변환을 두어 TypeScript와 JSX를 테스트 환경에서 실행한다.
- **React Testing Library**는 구현 상세 대신 실제 사용 방식과 접근 가능한 DOM을 기준으로 검증하게 해 리팩터링 내성을 높인다.
- **MSW**는 이미 브라우저와 Storybook용 핸들러가 있으므로 같은 네트워크 동작을 Node 통합 테스트에도 재사용할 수 있다.
- **Playwright**는 격리된 브라우저 컨텍스트, 자동 대기, 실패 trace를 제공해 라우팅과 반응형 회귀의 재현 단서를 남기기 좋다.
- **Storybook**은 현재 보유한 Story를 컴포넌트 상태 명세로 활용한다. Webpack builder를 유지하는 동안에는 Storybook Vitest addon을 성급히 결합하지 않고, 우선 Storybook 정적 빌드와 필요한 `play` 테스트부터 적용한다.

참고 문서:

- [React Testing Library 소개](https://testing-library.com/docs/react-testing-library/intro/)
- [Jest 시작하기](https://jestjs.io/docs/getting-started)
- [Jest 설정](https://jestjs.io/docs/configuration)
- [MSW 문서](https://mswjs.io/docs/)

## 4. 계층별 적용 기준

### 4.1 단위 테스트

DOM이나 네트워크 없이 결과를 확인할 수 있는 로직에 사용한다.

- API DTO를 화면 모델로 변환하는 파서
- 검색 쿼리와 주변 매장 요청 URL 생성
- OAuth callback 경로와 로그인 후 복귀 경로 검증
- JWT에서 회원 식별자를 읽는 로직
- 페이지네이션, 선택 상태, 필터처럼 순수 함수로 분리된 규칙

타입 검사로 이미 보장되는 단순 대입, 상수, 스타일 토큰은 테스트하지 않는다.

### 4.2 통합 테스트

페이지 또는 의미 있는 기능 단위로 렌더링하고 사용자의 입력부터 화면 결과까지 검증한다. 자식 컴포넌트를 무조건 모킹하지 않고, 네트워크와 브라우저 외부 경계만 대체한다.

- 검색어 입력과 결과 선택
- 로딩 중 기존 결과 유지, 빈 결과, API 오류와 다시 시도
- 지도 마커 선택과 목록 카드 포커스의 선택 상태 연결
- 비로그인 사용자의 보호 기능 진입과 로그인 화면 이동
- OAuth callback 성공·실패, 토큰 저장, 원래 페이지 복귀
- 마이페이지 회원 정보 조회·수정·탈퇴 및 문의 전송 상태
- 매장 상세의 사진·편의시설·보유 가챠 성공·빈 상태·오류 상태

지도 레이아웃 계산처럼 jsdom이 실제로 계산하지 못하는 값은 억지로 단언하지 않는다. 지도 SDK adapter가 받은 좌표와 명령을 검증하고 실제 드래그·줌은 E2E 또는 수동 점검으로 보완한다.

### 4.3 E2E 테스트

전체 기능을 E2E로 중복하지 않고, 사용자가 서비스를 이용할 수 있는지를 보여주는 짧은 여정만 둔다.

초기 필수 시나리오는 다음과 같다.

1. 앱 진입 → 가챠 검색 → 매장 결과 확인 → 매장 상세 진입
2. 비로그인 상태에서 보호 기능 진입 → 로그인 화면 이동 → 복귀 경로 보존
3. 잘못된 매장 또는 API 오류 → 안내와 다시 시도 노출
4. 데스크톱과 모바일 뷰포트에서 핵심 탐색 컨트롤 사용 가능

카카오·네이버의 실제 로그인 화면과 실제 카카오 지도 서버는 PR E2E에서 호출하지 않는다. 우리가 제어하지 못하는 화면, 계정, 네트워크 때문에 PR이 실패하지 않도록 OAuth callback 응답과 지도 경계는 테스트 환경에서 제어한다. 실제 제공자 연동은 개발 서버 배포 후 릴리스 체크리스트에서 한 번 확인한다.

E2E 실패 시 첫 재시도에 trace를 남기고 CI 산출물로 보관한다. 무조건 여러 번 재시도해 실패를 숨기지 않는다.

### 4.4 시각적·접근성 테스트

- 재사용 컴포넌트와 주요 페이지에 기본, 로딩, 빈 결과, 오류, 긴 텍스트 Story를 유지한다.
- 모바일 약 360px, 태블릿 768px 전후, 데스크톱을 대표 뷰포트로 둔다.
- 먼저 `build-storybook`을 PR 필수 검사로 삼아 모든 Story가 정적으로 빌드되는지 확인한다.
- Story의 상호작용은 `play` 함수로 작성하고 버튼 이름, 다이얼로그 포커스, 키보드 닫기처럼 사용자 행동을 검증한다.
- 자동 이미지 비교는 팀이 기준 이미지 검토 책임과 서비스 비용을 합의한 후 Chromatic 같은 도구를 별도 이슈로 도입한다.
- 거대한 DOM snapshot은 작은 의도적 마크업 계약 외에는 사용하지 않는다.

홈, 채팅, 중고거래처럼 새 기능이 병합되면 같은 표에 위험도와 사용자 여정을 추가한다. 화면 파일 수에 비례해 테스트를 만드는 방식은 사용하지 않는다.

## 6. 테스트 구조와 작성 규칙

```text
frontend/
├── src/
│   ├── ...
│   └── test/
│       ├── setup.ts
│       ├── server.ts
│       └── renderWithProviders.tsx
├── e2e/
│   ├── fixtures/
│   └── *.spec.ts
├── babel.config.cjs
├── jest.config.cjs
└── playwright.config.ts
```

- 단위·통합 테스트는 대상과 가까운 `*.test.ts` 또는 `*.test.tsx`로 둔다.
- 전체 앱 Provider 조합, 공통 MSW server, 브라우저 API 초기화만 `src/test`에 둔다.
- 테스트 데이터는 필요한 필드만 명확히 바꿀 수 있는 factory를 사용한다. 하나의 거대한 fixture를 모든 테스트가 공유하지 않는다.
- 기본 MSW 핸들러는 정상 응답을 제공하고 테스트별 오류·빈 결과는 해당 테스트에서 덮어쓴 뒤 초기화한다.
- 시간, 위치, 난수에 의존하는 로직은 고정 가능한 입력으로 주입한다.
- 테스트 제목은 구현이 아니라 조건과 사용자가 보는 결과를 한국어 또는 팀이 합의한 한 언어로 표현한다.

## 7. CI 품질 게이트

검증과 배포를 한 job에 묶지 않는다. PR용 `Frontend Quality` 워크플로를 GitHub-hosted runner에서 먼저 실행하고, 통과한 코드만 배포 브랜치로 병합한다. self-hosted dev/prod runner는 배포 역할에 집중시킨다.

`Frontend Quality`의 안정적인 job 이름은 `Frontend Quality`로 유지한다. 워크플로가 병합된 뒤 저장소 관리자는 `frontend-dev`와 `main`의 브랜치 보호 규칙에서 이 검사를 required status check로 지정한다. 이 저장소 설정 전까지는 워크플로가 실패를 알려주지만 병합 자체를 강제로 막지는 않는다.

### 모든 프론트엔드 PR

1. `pnpm install --frozen-lockfile`
2. `pnpm lint`
3. `pnpm format:check`
4. `pnpm typecheck`
5. `pnpm test --runInBand --coverage`
6. `pnpm build-storybook`
7. `pnpm build`

핵심 Chromium E2E는 P0 단위·통합 테스트가 안정된 뒤 별도 이슈에서 품질 게이트에 추가한다. 시각적 회귀도 같은 방식으로 후속 도입한다.

`frontend/**` 또는 관련 workflow가 바뀐 PR에만 실행하고, 동일 SHA의 중복 설치와 빌드는 캐시·job 구성으로 줄인다. `frontend-dev`와 `main` 보호 규칙에는 이 품질 검사를 required status check로 등록한다.

### 릴리스 전 또는 정기 실행

- Chromium, Firefox, WebKit E2E
- 대표 뷰포트 시각적 회귀
- 실제 개발 API를 이용한 검색·로그인 smoke test

외부 OAuth와 실제 지도 SDK를 포함한 검사는 운영 배포의 필수 자동 게이트로 두지 않고, 개발 서버의 짧은 수동 smoke checklist로 관리한다.

## 8. 커버리지와 실패 처리

- 첫 도입 PR에서는 숫자를 맞추기 위한 테스트를 만들지 않도록 리포트만 수집한다.
- P0 테스트가 자리 잡은 뒤 현재 수치를 기준선으로 저장하고 새 코드가 기준선을 낮추지 않게 한다.
- 인증, 라우팅, DTO 파서처럼 실패 영향이 큰 모듈은 분기 커버리지를 별도로 확인한다.
- 커버리지가 높아도 핵심 사용자 시나리오가 빠졌다면 완료로 보지 않는다.
- flaky test는 재시도 횟수를 늘려 덮지 않는다. 담당 이슈를 만들고 원인을 해결하며, 불가피하게 격리할 때는 기한과 복구 조건을 남긴다.
- CI 실패 산출물에는 Playwright trace, 스크린샷, 테스트 리포트를 보관해 로컬에서 재현할 단서를 제공한다.

## 9. 도입 순서

각 단계는 별도 이슈와 작은 PR로 진행한다.

1. **전략 합의 (완료)**: 이 문서를 리뷰하고 P0 시나리오와 도구를 확정한다.
2. **기반 구축 (완료)**: Jest, Testing Library, jsdom, MSW Node server, 공통 render와 `test` 스크립트를 추가한다.
3. **P0 단위·통합 테스트 (완료)**: 아래의 합의된 시나리오를 작성하고 이번 제출 범위를 완료한다.
4. **PR 품질 워크플로 (워크플로 완료, 저장소 설정 필요)**: 정적 검사, 단위·통합 테스트, Storybook/앱 빌드를 실행하고 브랜치 보호 규칙의 required check로 연결한다.
5. **E2E 기반과 smoke 여정**: Playwright Chromium과 핵심 3~4개 여정을 추가한다.
6. **P1 회귀 테스트**: 지도·목록 연결, 매장 상세, 마이페이지를 보강한다.
7. **시각적·접근성 자동화**: Story 보강 후 팀이 선택한 시각 비교 도구를 연결한다.
8. **배포 게이트 정비**: 검증 완료 후 dev 자동 배포, 태그/릴리스와 승인에 따른 prod 배포 순서를 확정한다.

### 이번 제출 범위

P0 단위 테스트는 DOM 없이 다음 순수 로직을 검증한다.

1. 로그인 후 복귀 주소 검증
2. OAuth callback 경로 검증
3. JWT 회원 식별자 파싱

P0 통합 테스트는 실제 컴포넌트와 Context를 렌더링하고 MSW로 네트워크 경계만 제어해 다음 흐름을 검증한다.

1. 검색어 입력 → 결과 표시 → 결과 선택 → 검색 페이지 이동
2. 비로그인 사용자가 마이페이지 접근 → 로그인 이동 → 복귀 주소 유지
3. OAuth callback 성공 → 토큰 저장 → 회원 조회 → 원래 페이지 복귀
4. 잘못된 callback 또는 API 오류 → 오류 화면과 다시 시도
5. 잘못된 URL → 홈 이동

E2E와 시각적 회귀는 이번 제출물에서 제외하고 후속 이슈에서 추가한다. 외부 OAuth 제공자와 실제 지도 SDK를 자동 테스트에서 직접 호출하지 않는 원칙은 후속 테스트에도 유지한다.

## 10. 완료 기준

- 팀원이 새 기능에 어떤 테스트를 추가할지 이 문서만 보고 결정할 수 있다.
- 검색·인증·라우팅 P0 단위·통합 흐름에 Jest 자동화 테스트가 있다.
- 로컬에서 정적 검사, 테스트, Storybook 빌드와 앱 빌드를 실행할 수 있다.
- 후속 CI 이슈에서 필수 검사를 `frontend-dev`와 `main`의 병합 조건으로 연결할 수 있다.
- 배포 후 발견된 버그에는 가능한 경우 재발 방지 테스트가 함께 추가된다.

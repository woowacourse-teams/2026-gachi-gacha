# 앱 출시 이벤트 접수 운영

## 현재 상태

이 문서는 `app-launch-2026`, `schemaVersion: 2` 전용 접수 계약이다. 기존 인기 굿즈 이벤트 및 이름·전화번호·사연·사진을 받던 v1과 호환되지 않는다. **새 Google 시트와 새 Apps Script 프로젝트를 사용한다. 코드 병합만으로 Google 저장소가 생성되거나 접수가 활성화되지는 않는다.**

- 경품: 4종 각 2개, 총 8명에게 1인 1개 무작위 증정. 중복 당첨 제외.
- 입력: 이름, 인스타그램 아이디. 전화번호·사연·사진은 받지 않는다.
- 제출 순간 기존 인증 API로 회원번호와 현재 조회 가능한 본인의 모든 교환글 ID를 수집한다. 교환 상태 필터 없이 끝 페이지까지 조회하며, 삭제된 글은 복원할 수 없다.
- 같은 회원이 다시 응모하면 최신 정보와 교환글 목록으로 1행을 갱신한다. 반복 클릭 횟수 자체가 추첨 기회를 늘리지는 않는다.
- 일정: 안내·응모 시작 11/10, 최종 마감 11/27. 사용자가 마지막으로 정정한 시작일을 적용한다. 시각은 한국 시간 00:00 시작, 11/27 23:59까지로 설정한다. 종료 값은 **11/28 00:00 미포함**이다.
- 당첨자는 인스타그램 DM으로 개별 안내한다. 이전 시안의 11/27 발표일은 더 이상 사용하지 않는다. 발표 시각은 별도 확정한다.
- 미확정: 개인정보 처리 주체, 문의 연락처, 수집 목적의 확정 문구, 보관기간, 동의 문구 버전.
- 배너 공개와 실제 접수를 분리한다. DEV는 11/16부터 배너를 미리 볼 수 있지만, 저장소·정책·브라우저 검증 전에는 서버 `ACCEPTING=false`를 유지한다.

정상 웹 화면에서는 기존 서비스 로그인과 인증 API 응답을 확인한다. 그러나 공개 Google Apps Script는 가치가챠 세션을 검증하지 않는다. 직접 HTTP 요청을 만드는 사람은 제출 회원번호·글 ID를 위조할 수 있으므로 시트에는 **자가신고/미검증**으로 기록한다. 회원번호로 갱신하는 구조도 인증 증명이 아니며 타인 번호를 이용한 변조를 서버에서 막지는 못한다. 앱 설치·글 소유권·활동·중복 당첨을 운영자가 검증해야 한다. 이러한 수동 검증으로 충분한지 접수 전에 결정하고, 엄격한 인증 접수가 필요하면 신뢰할 수 있는 서버가 회원과 글을 검증하는 별도 계약이 필요하다. 이 작업에서는 백엔드 코드를 변경하지 않았다. 액세스 토큰·리프레시 토큰·쿠키를 Google로 보내지 않는다.

상품 이미지의 웹사이트 재사용 허락은 확인되지 않았다. 사용자 요청에 따라 상품 식별용으로 연결했으며, 다른 사이트의 사용 사례·출처 표시·비협찬 안내가 이용 허락을 대신하거나 저작권 위험을 없애지는 않는다. 별도로 허락받은 이미지 또는 직접 촬영한 사진으로 교체할 수 있다. 원본에 포함된 표시는 임의로 제거하지 않았다.

### 이전 이벤트 링크

기존 마이페이지 진입 메뉴는 제거하고 `/events/popular-goods`는 새 상세 주소 `/events/app-launch`로 이동한다. 과거 폼이 새로운 Apps Script에 이전 필드를 보내지 않도록 실제 라우팅에서 분리했다. 기존 시트·스크립트는 수정하지 않았다.

1. 팀이 관리하는 Google 계정으로 **새 Apps Script 프로젝트**를 만든다. 기존 이벤트 프로젝트는 수정하지 않는다.
2. `frontend/scripts/launch-event-apps-script/Code.gs`를 복사한다.
3. `setupLaunchEventStorage()`를 한 번 실행하고 필요한 Google 권한을 확인한다.
4. 스크립트 속성에서 `SPREADSHEET_ID`가 만들어졌는지 확인한다. 시트 제목은 **가치가챠 앱 출시 이벤트 v2 응모**, 탭은 **응모 / 접수이력**이다. 테스트용 제목에는 `DEV`를 붙이는 것을 권장한다. 재실행 방지 검사가 있으므로 기존 ID를 지워 반복 실행하지 않는다.
5. 생성된 시트는 비공개다. 링크 공개를 켜지 말고 실제 담당자에게만 필요한 권한을 부여한다. 워크스페이스 정책·상속 권한도 확인한다. 사진 폴더는 만들지 않으며, Drive 권한은 시트의 비공개 설정·확인에만 사용한다.

설정 함수가 중간에 실패했다면 Google Drive에 일부 자원이 생겼을 수 있다. 자동 재실행하지 말고 생성 내역과 스크립트 속성을 먼저 확인한다. 실제 POST에서도 시트의 링크 공유가 비공개인지 검사하지만, 담당자별 직접 공유·조직 권한까지 자동 감사하지는 않는다.

자동 생성되는 `응모` 탭의 열:

| 열                                              | 용도                                                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------------- |
| 최초접수일시 / 최종접수일시 / 이벤트ID / 접수ID | 최초 및 최신 서버 접수 시각, 캠페인, UUID 재시도 식별                         |
| 자가신고회원ID / 이름 / 인스타그램ID            | 회원별 최신 정보, DM 연락 대상                                                |
| 자가신고교환글수 / 자가신고교환글ID목록1~5      | 최종 제출 시점의 글 수와 ID. 최대 10,000개를 2,000개씩 나눠 셀 크기 제한 방지 |
| 개인정보동의 / 유의사항동의 / 약관버전          | 접수 당시 동의 기록                                                           |
| 요청해시                                        | 같은 UUID로 다른 내용을 보내는 경우 거절                                      |
| 삭제예정일                                      | 이벤트 종료 시각 + 설정 보관일수                                              |
| 운영검증상태                                    | 기본 `미검증`. 재응모하면 재검증을 위해 초기화                                |
| 접수횟수                                        | 갱신 이력 순서 확인용. 추첨 가중치가 아님                                     |

`접수이력` 탭에는 `이벤트ID, 접수ID, 자가신고회원ID, 요청해시, 접수일시, 최초접수일시, 접수횟수, 삭제예정일`을 보관한다. 이름·인스타그램·전체 글 목록의 과거 사본은 추가 보관하지 않는다. 동일 요청 재시도와 오래된 요청을 구분하기 위한 기술 이력이다.

헤더 이름·순서를 변경하면 접수가 중단된다. 회원번호 등은 텍스트로 저장하고 수식 시작 문자를 방어한다. 개인정보가 들어 있는 행을 GitHub 이슈·스크린샷·공개 문서에 올리지 않는다. 접수 중에는 이력 행을 지우지 않는다.

### 참여 활동 안내와 수집 기준

화면 문구: **가치가챠에서 교환 이야기를 활발하게 나눌수록, 선물을 만날 기회도 커져요.**

- 최종 응모 버튼을 누를 때 `/api/v1/trades/me`를 끝 페이지까지 조회한다. 최초 20개만 저장하지 않는다.
- 이름·인스타그램 외에 회원번호, 교환글 수·ID, 동의·접수 기록도 수집 항목에 고지한다.
- 조회 오류·로그인 변경·데이터 누락·30초 초과 시 불완전한 목록을 제출하지 않는다.
- 응모 뒤 작성한 글을 반영하려면 다시 응모해야 한다. 시트가 이후 활동을 자동 수집하지 않는다.
- 추첨 알고리즘이나 게시글당 가중치는 구현하지 않았다. 공개 전 유효 활동·도배 제외 기준과 실제 추첨 방식을 팀에서 확정한다.

## 2. 서버 설정 확정

Apps Script 프로젝트 설정 → 스크립트 속성에서 값을 지정한다. 개인 계정의 비공개 주소를 임의로 넣거나 예시 정책을 실제 동의문으로 사용하지 않는다.

| 속성                     | 입력 기준                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| `ACCEPTING`              | 준비 중 `false`, 모든 검증 후 `true`                                                     |
| `START_AT`               | `2026-11-10T00:00:00+09:00`. DEV도 같은 시각을 사용하며 실제 접수는 `ACCEPTING`으로 제어 |
| `END_AT`                 | `2026-11-28T00:00:00+09:00` — 11/27 하루 전체까지, 이 시각은 미포함                      |
| `PRIVACY_CONTROLLER`     | 실제 처리 주체 이름                                                                      |
| `PRIVACY_CONTACT`        | 실제 이용 가능한 문의 채널                                                               |
| `PRIVACY_PURPOSE`        | 실제 수집·이용 목적                                                                      |
| `PRIVACY_RETENTION_DAYS` | 실제 보관일수, 정수 1~365. 법적 적합성을 자동 보장하는 값이 아님                         |
| `RULES_VERSION`          | 확정된 동의문 식별자. 목적·항목·기간 등 변경 시 반드시 변경                              |
| `MAX_SUBMISSIONS`        | 서로 다른 회원 수 상한, 기본 1000, 허용 1~10000                                          |
| `MAX_RECEIPTS`           | 기술 접수 이력 상한, 기본·최대 100000. 상한 시 `RECEIPT_CAPACITY_REACHED`로 거절         |

`PRIVACY_RETENTION_DAYS`는 **이벤트 종료 후** 보관일수다. 목적 문구 초안은 `이벤트 참여 확인, 추첨 및 당첨자 인스타그램 DM 연락`이며 실제 운영 방침에 맞춰 확정한다. 처리 주체·문의 채널·보관일수는 임의 확정하지 않는다. Google 보관·이전 및 동의 범위도 담당자가 검토한다. 이 문서나 코드만으로 법적 적합성이 보장되지 않는다.

접수 이력 상한에 도달했다고 진행 중 이력을 삭제해 공간을 만들면 과거 UUID 보호가 깨진다. 접수를 중단하고 운영 방식을 조정한다. 정책·일정 변경 시 이미 접수된 동의와 삭제 예정일도 함께 검토한다.

빈 정책·잘못된 일정·미설정 저장소는 서버가 접수를 거절한다. 유효하지 않은 메타데이터를 받은 프론트엔드도 폼 활성화를 막는다.

## 3. 웹 앱 배포와 개발 환경 연결

1. 새 웹 앱 배포를 만든다. 실행자는 관리 계정, 접근은 외부 브라우저가 로그인 없이 호출할 수 있는 범위로 설정한다. 조직 정책이 허용하지 않으면 인증 우회를 하지 말고 연결 방식을 다시 정한다.
2. `/macros/s/.../exec` 주소를 사용한다. 테스트용 `/dev` 주소는 허용하지 않는다.
3. GitHub의 **개발 환경** 변수에 아래 값을 저장한다. 운영 환경 변수는 별도 승인 없이 바꾸지 않는다.

```text
EVENT_APPLICATION_CAMPAIGN_ID=app-launch-2026
EVENT_APPLICATION_ENDPOINT=https://script.google.com/macros/s/배포ID/exec
EVENT_APPLICATION_BANNER_START_AT=2026-11-16T00:00:00+09:00
EVENT_APPLICATION_START_AT=2026-11-10T00:00:00+09:00
EVENT_APPLICATION_END_AT=2026-11-28T00:00:00+09:00
EVENT_APPLICATION_ENABLED=true
```

GitHub 경로: 저장소 → Settings → Environments → **frontend-development** → Environment variables. 운영은 별도 **frontend-production**이다. 배너만 미리 볼 때는 endpoint를 연결하지 않아도 된다. 운영 배너·응모 시작은 모두 `2026-11-10T00:00:00+09:00`을 기준으로 한다.

**GitHub 변수 저장만으로 이미 배포된 화면이 바뀌지는 않는다.** Webpack이 빌드 때 값을 주입하므로 변경 후 해당 환경을 다시 빌드·배포한다. 현재 배포하고 싶은 최신 커밋의 배포 작업을 재실행해야 하며, 오래된 실행을 재실행하면 코드도 과거 버전으로 배포할 수 있다. 웹 및 같은 원격 웹 주소를 여는 WebView는 새 페이지를 로드하면 적용된다. 이미 열린 앱 화면은 새로고침/재진입이 필요할 수 있다. 웹 콘텐츠 변경만으로 네이티브 재빌드가 필요하지는 않지만 앱 심사·네이티브 변경과는 별개다.

설정된 종료 시각에는 추가 배포 없이 배너가 숨겨진다. 열린 화면은 약 30초 간격 및 화면 복귀 때 재검사한다. 사용자가 기기 시계를 조작할 수 있으므로 접수 마감은 Apps Script의 서버 시각으로도 강제한다.

응모 시작·종료 시각을 바꿀 때는 GitHub 변수와 Apps Script `START_AT`/`END_AT`를 함께 맞춘다. 일정이 다르면 폼을 열지 않는다. 긴급 접수 중단은 **Apps Script `ACCEPTING=false`**로 즉시 적용하며 기존에 열린 폼도 서버가 거절한다. 배너까지 즉시 원격 제어하려면 별도 런타임 설정 배포 방식이 필요하다. 현재 구현이 그 기능을 제공한다고 안내하지 않는다.

### 실제 접수를 열기 전 필수 검증

- 별도 테스트 프로젝트/시트에 테스트 계정·입력으로 GET·POST를 수행한다.
- Android 웹뷰/Chrome, iOS 웹뷰/Safari에서 메타데이터 GET과 POST 응답을 실제로 읽는지 확인한다. Apps Script 리다이렉트·CORS·조직 접근 정책은 단위 테스트가 보장하지 않는다.
- 이름·인스타그램·회원번호·모든 페이지의 글 ID·동의 버전이 정확한 열에 저장되는지 확인한다. `@`와 대소문자는 정규화한다.
- 같은 회원으로 글 추가 후 재응모하면 새 행이 아니라 최신 1행으로 갱신되는지 확인한다.
- 같은 UUID·같은 내용 재시도는 한 행과 같은 영수증을 반환한다. 같은 UUID·다른 내용은 거절한다.
- 오래된 요청을 뒤늦게 재시도해도 더 최신의 응모 정보를 덮어쓰지 않는지 확인한다.
- 마감 직전 이력만 저장되고 응모 행 갱신에 실패한 요청은 기존 UUID·해시가 같을 때 원래 보관기한 안에서 복구할 수 있다. 이는 이미 받은 요청 확인이며 신규 접수 연장이 아니다. 일반 화면의 마감 후 신규 제출은 계속 차단한다.
- HTML 로그인 페이지·빈 응답·잘못된 캠페인·마감·동의 누락·정책 버전 변경은 완료 화면으로 넘어가지 않는다.
- 실패·시간 초과 시 입력을 유지한다. 다음 시도에서 활동을 다시 확인하고 내용이 같으면 이전 접수ID, 입력·글 목록·정책이 바뀌었으면 새 접수ID를 사용한다. 서버에는 저장됐지만 응답만 못 받은 경우가 있을 수 있다.
- 준비 완료 후에만 새 운영 저장소 설정, GitHub 활성화 및 재빌드, 서버 `ACCEPTING=true`를 진행한다. 서버 일정과 프론트엔드 일정이 다르면 접수는 열리지 않는다.

공개 Apps Script URL에는 로그인하지 않은 직접 요청도 들어올 수 있다. 접수 상한과 잠금은 중복·동시 쓰기를 줄이는 장치이며 봇 방지나 회원 인증을 대신하지 않는다. 실제 공격·할당량 부족 시 먼저 접수를 닫고 서버 검증/속도 제한 도입을 검토한다.

### 연결을 위해 전달할 것

- 새 웹 앱 **`/exec` URL**. `/dev` 또는 시트 공유 URL이 아니다.
- 확정한 처리 주체, 문의 채널, 목적, 종료 후 보관일수, 동의문 버전.
- DEV/운영의 응모 시작 시각. 준비 확인 전에는 `ACCEPTING=false` 유지.
- 액세스 토큰, Google 로그인 정보, 실제 응모자 명단은 전달하지 않는다. 스프레드시트는 공개 공유할 필요 없다.

## 4. 전송 계약

요청은 `text/plain;charset=UTF-8` JSON이다. 허용 필드는 `eventId, schemaVersion, submissionId, memberId, name, instagramId, tradeIds, privacyConsent, rulesConsent, rulesVersion`이다. 서버는 캠페인·v2 스키마·동의·정책 버전·기간·문자 길이·고유한 양의 안전 정수 ID·본문 상한(256KiB)을 검사한다. 토큰·전화번호·사연·사진 등 계약 밖 필드는 거절한다.

성공 응답:

```json
{
  "ok": true,
  "eventId": "app-launch-2026",
  "submissionId": "019ab251-394e-4a77-9c21-1221ea123456",
  "receivedAt": "2026-11-12T00:00:00.000Z"
}
```

`ok`만 있는 기존 응답은 성공으로 인정하지 않는다. 응답의 접수ID·이벤트ID·시각을 확인한 후 완료 화면을 표시한다. 이것은 **접수 확인**이며 자격 검증·당첨 확인은 아니다. 잠금 안에서 접수이력을 먼저 기록한 다음 최신 응모 행을 갱신하고, 중간 실패는 같은 요청 재시도로 복구한다. 서버는 마감·중단·정책 변경 후에도 기존 UUID와 원래 해시가 같은 요청만 원래 보관기한 안에서 확인·복구한다. 신규 요청은 현재 일정·정책을 따라야 한다. 두 시트가 데이터베이스 트랜잭션인 것은 아니므로 오류가 반복되면 접수를 닫고 두 탭을 담당자가 대조한다.

## 5. 보관기간 종료와 정리

1. `ACCEPTING=false`로 닫는다.
2. `cleanupExpiredEntries()`를 실행한다. 인자를 생략하면 만료 대상 **개수만** 반환한다.
3. 담당자가 보관 기준과 대상 수를 확인한 뒤 `cleanupExpiredEntries(false)`를 실행한다. 이벤트 종료 후 보관기한이 지난 해당 이벤트의 응모 행과 접수이력만 삭제한다. 접수 기간 중 이력은 삭제하지 않는다.
4. 시트 버전 기록, 다운로드한 CSV·복사본 등 잔존 자료도 확정된 보관 정책에 따라 정리한다. 행 삭제는 모든 사본의 영구 삭제를 보장하지 않는다.
5. 저장소 오류가 발견되면 출처를 확인하기 전에 광범위 삭제나 재실행으로 우회하지 않는다.

자동 삭제 트리거는 코드만으로 설치되지 않는다. 운영자는 삭제 일정을 등록하고 결과를 확인해야 한다. 마지막에는 웹 앱 배포 중지·접근 권한 회수 및 필요하지 않은 보관 사본을 점검한다.

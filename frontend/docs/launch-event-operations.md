# 앱 출시 이벤트 접수 운영

## 현재 상태

이 문서는 `app-launch-2026`, `schemaVersion: 3` 전용 접수 계약이다. 브라우저가 Google Apps Script에 직접 회원번호를 제출하던 v2와 호환되지 않는다. 사용자에게 회원번호를 입력받지 않고, **프론트엔드 소유의 인증 중계 서버가 기존 인증 API로 회원·교환글을 확인한 뒤 서명한 요청만 저장한다.** 기존 인기 굿즈 이벤트 및 전화번호·사연·사진을 받던 v1도 이 계약과 분리한다.

코드와 설치 예제를 준비한 상태이며, 실제 EC2 중계 서버 설치·Google 스크립트 재배포·끝까지 접수하는 실기기 검증이 완료됐다는 뜻은 아니다. **코드 병합만으로 Google 저장소가 생성되거나 접수가 활성화되지 않는다. 아래 준비와 DEV 검증이 끝날 때까지 `ACCEPTING=false`를 유지한다. 운영 서버·운영 환경 설정은 이 절차의 대상이 아니다.**

GitHub DEV에 남아 있는 이전 Google 직결 endpoint는 중계 서버·GAS 준비 전에 변경하지 않았다. schema3 프론트엔드는 그 주소를 유효한 제출 대상으로 인정하지 않으므로 설정이 덜 된 상태에서 옛 직접 제출 경로를 열지 않는다. 아래 상대경로로의 변수 변경은 실제 연결 준비 후 수행할 작업이다.

- 경품: 4종 각 2개, 총 8명에게 1인 1개 무작위 증정. 중복 당첨 제외.
- 입력: 이름, 인스타그램 아이디. 전화번호·사연·사진은 받지 않는다.
- 제출 순간 기존 인증 API로 회원번호와 현재 조회 가능한 본인의 모든 교환글 ID를 수집한다. 교환 상태 필터 없이 끝 페이지까지 조회하며, 삭제된 글은 복원할 수 없다.
- 같은 회원이 다시 응모하면 최신 정보와 교환글 목록으로 1행을 갱신한다. 반복 클릭 횟수 자체가 추첨 기회를 늘리지는 않는다.
- 일정: 안내·응모 시작 11/10, 최종 마감 11/27. 사용자가 마지막으로 정정한 시작일을 적용한다. 시각은 한국 시간 00:00 시작, 11/27 23:59까지로 설정한다. 종료 값은 **11/28 00:00 미포함**이다.
- 당첨자는 인스타그램 DM으로 개별 안내한다. 이전 시안의 11/27 발표일은 더 이상 사용하지 않는다. 발표 시각은 별도 확정한다.
- 2026-11-16 운영자 승인: 처리 주체 `가치가챠팀`, 문의 `Instagram @gachi__.gacha`, 아래의 수집 목적·동의문 및 경품 전달 완료 후 지체 없이 삭제/최대 이벤트 종료 후 30일 보관. 스크립트 속성에 실제 적용하고 수신부 인증을 검증하기 전에는 접수를 열지 않는다.
- 배너 공개와 실제 접수를 분리한다. DEV는 11/16부터 배너를 미리 볼 수 있지만, 저장소·정책·브라우저 검증 전에는 서버 `ACCEPTING=false`를 유지한다.

### 인증과 저장의 경계

```text
웹 / 같은 웹 주소를 여는 앱
  → 같은 출처의 /event-api/launch-event
  → 프론트엔드 인증 중계 서버 (127.0.0.1:3101)
      → 기존 /api/v1/members/me로 액세스 토큰 인증 확인
      → 기존 /api/v1/trades/me의 모든 페이지와 글 소유자 확인
      → 접수 본문·시각을 HMAC 서명
  → Apps Script 서명 검증
  → 비공개 응모 / 접수이력 시트
```

- 비로그인 사용자는 로그인으로 이동하고 `/events/app-launch?apply=1`로 돌아온다. 복귀 후 폼을 열어 사용자가 동의하고 최종 제출하며 **로그인만으로 자동 응모하지 않는다.**
- 브라우저의 `expectedMemberId`는 입력 도중 계정이 바뀌었는지 대조하는 보조 값이다. 접수 회원번호의 근거로 신뢰하지 않으며 브라우저가 보낸 `memberId`·`tradeIds`는 중계 서버가 거절한다.
- 중계 서버는 기존 회원 API가 **동일한 토큰을 인증한 다음에만** 토큰의 회원번호를 읽는다. 토큰을 디코딩하는 행위만으로 인증 성공으로 처리하지 않는다. 회원 API 응답에 회원번호가 있으면 일치 여부도 확인한다.
- 중계 서버는 고정된 신뢰 API 주소만 호출하고 API 리다이렉트를 따라가지 않는다. 액세스 토큰은 우리 중계 서버와 기존 인증 API에만 전달하며 Google 본문·시트에 넣지 않는다. 리프레시 토큰·쿠키도 Google에 전달하지 않는다.
- Apps Script는 공유 비밀키를 사용하는 HMAC 서명과 시각을 검사한다. 공개 `/exec` 주소를 안다고 직접 회원번호를 제출할 수는 없다. 이것이 Google 계정 로그인이나 봇·할당량 문제 전체를 해결하는 것은 아니다.
- **회원·게시글 확인과 앱 설치·추첨 자격 확인은 다르다.** 앱 설치 여부, 유효 활동·도배 제외, 중복 당첨은 별도 운영 확인 대상이다. 이 작업에서 백엔드 코드는 변경하지 않는다.

화면의 경로·대체 텍스트는 `src/features/launchEvent/launchEventContent.ts`에서 교체한다. 실제 화면용 이미지는 원본 비율을 유지하고, 경품 안내는 지연 로드한다. 글자가 들어간 이미지의 핵심 내용은 주변 HTML로도 제공한다.

상품 이미지의 웹사이트 재사용 허락은 확인되지 않았다. 사용자 요청에 따라 상품 식별용으로 연결했으며, 다른 사이트의 사용 사례·출처 표시·비협찬 안내가 이용 허락을 대신하거나 저작권 위험을 없애지는 않는다. 별도로 허락받은 이미지 또는 직접 촬영한 사진으로 교체할 수 있다. 원본에 포함된 표시는 임의로 제거하지 않았다.

### 이전 이벤트 링크

기존 마이페이지 진입 메뉴는 제거하고 `/events/popular-goods`는 새 상세 주소 `/events/app-launch`로 이동한다. 과거 폼이 새로운 Apps Script에 이전 필드를 보내지 않도록 실제 라우팅에서 분리했다. 기존 시트·스크립트는 수정하지 않았다.

### 이미 직접 만든 시트를 연결하는 현재 절차

사용자는 **가치가챠 앱 출시 이벤트 v2 응모** 시트와 **응모 / 접수이력** 탭을 직접 만들었다. **이 경우 `setupLaunchEventStorage()`를 실행하지 않는다.** 해당 함수는 별도 새 시트를 생성하는 용도이며, 현재 시트를 연결하는 함수가 아니다.

1. 직접 만든 시트에서 **확장 프로그램 → Apps Script**를 열고 `frontend/scripts/launch-event-apps-script/Code.gs`를 복사한다. 과거 이벤트 프로젝트는 수정하지 않는다.
2. 시트 주소의 `/spreadsheets/d/시트ID/edit`에서 시트ID만 복사해 스크립트 속성 `SPREADSHEET_ID`에 넣는다. 시트 공유 URL 전체를 넣지 않는다.
3. 아래 서버 설정을 입력하고 `ACCEPTING=false`를 유지한다. 실제 테스트를 위한 별도 시트에는 제목에 `DEV`를 붙이는 것을 권장한다.
4. 링크 공개를 켜지 말고 실제 담당자에게만 필요한 권한을 부여한다. 워크스페이스 정책·공유 드라이브의 상속 권한도 확인한다. 사진 폴더는 만들지 않는다.
5. `응모`의 첫 행은 코드의 `HEADERS`, `접수이력`의 첫 행은 `RECEIPT_HEADERS`와 이름·순서가 일치해야 한다. 아래 열 설명을 참고하되 임의로 이름을 줄이거나 순서를 바꾸지 않는다. 이전 `자가신고` 헤더가 있다면 다음 전환 절차를 사용한다.

### 기존 v2 헤더를 전환하는 경우

시트 제목의 `v2`는 사용자가 정한 이름이므로 유지한다. 접수 계약의 `schemaVersion: 3`과 시트 제목은 별개다.

- **`ACCEPTING=false`, 비공개 공유, 두 탭 모두 첫 행의 헤더만 있는 상태**에서만 `migrateEmptyLaunchEventStorageToVerified()`를 명시적으로 실행한다.
- 함수는 두 탭의 크기와 기존/새 헤더를 먼저 모두 확인한 뒤 `자가신고회원ID`·`자가신고교환글수`·`자가신고교환글ID목록1~5`를 새 헤더로 바꾼다. 새 시트를 생성하지 않는다.
- **어느 탭이든 기존 데이터가 한 행이라도 있으면 중단한다.** 이전 미검증 데이터를 이름만 바꾸어 검증된 응모로 취급하지 않는다. 데이터를 지우고 재실행하지 말고 실제 기록·보관 근거를 확인한 뒤 별도 저장소 사용 여부를 담당자와 결정한다.
- 예상하지 못한 헤더·공유 권한·부분 오류가 있으면 그대로 멈춘다. 두 탭이 헤더만 있는 것을 재확인하지 않고 재실행하지 않는다.
- 같은 시트를 가리키는 **과거 서명 없는 Apps Script 웹 앱 배포는 보관 처리(Archive)하여 호출을 중단**한다. 새 배포를 만드는 것만으로 옛 URL이 사라지지는 않는다. 편집기의 최신 코드로 바꿨다고 옛 배포 버전까지 바뀌는 것도 아니다.

시트가 전혀 없는 경우에만 새 프로젝트에서 `setupLaunchEventStorage()`로 새 저장소를 만들 수 있다. 이미 ID가 있거나 설정 함수가 중간에 실패했다면 ID를 지우고 반복 실행하지 않는다. Google Drive의 생성 내역과 스크립트 속성부터 확인한다. 실제 POST에서도 시트의 링크 공유가 비공개인지 검사하지만, 담당자별 직접 공유·조직 권한까지 자동 감사하지는 않는다. 공유 드라이브에서 이 권한 검사가 정상 동작하는지도 실제 연결 테스트가 필요하다.

현재 코드가 요구하는 `응모` 탭의 열:

| 열                                              | 용도                                                                                 |
| ----------------------------------------------- | ------------------------------------------------------------------------------------ |
| 최초접수일시 / 최종접수일시 / 이벤트ID / 접수ID | 최초 및 최신 서버 접수 시각, 캠페인, UUID 재시도 식별                                |
| 회원ID / 이름 / 인스타그램ID                    | 인증된 회원별 최신 정보, DM 연락 대상                                                |
| 교환글수 / 교환글ID목록1~5                      | 중계 서버가 조회한 본인 글 수와 ID. 최대 10,000개를 2,000개씩 나눠 셀 크기 제한 방지 |
| 개인정보동의 / 유의사항동의 / 약관버전          | 접수 당시 동의 기록                                                                  |
| 요청해시                                        | 같은 UUID로 다른 내용을 보내는 경우 거절                                             |
| 삭제예정일                                      | 이벤트 종료 시각 + 설정 보관일수                                                     |
| 운영검증상태                                    | 기본 `로그인·게시글 확인 / 앱 설치 확인 필요`. 재응모하면 이 값으로 초기화           |
| 접수횟수                                        | 갱신 이력 순서 확인용. 추첨 가중치가 아님                                            |

`접수이력` 탭에는 `이벤트ID, 접수ID, 회원ID, 요청해시, 접수일시, 최초접수일시, 접수횟수, 삭제예정일`을 보관한다. 이름·인스타그램·전체 글 목록의 과거 사본은 추가 보관하지 않는다. 동일 요청 재시도와 오래된 요청을 구분하기 위한 기술 이력이다.

헤더 이름·순서를 변경하면 접수가 중단된다. 회원번호 등은 텍스트로 저장하고 수식 시작 문자를 방어한다. 개인정보가 들어 있는 행을 GitHub 이슈·스크린샷·공개 문서에 올리지 않는다. 접수 중에는 이력 행을 지우지 않는다.

### 참여 활동 안내와 수집 기준

화면 문구: **가치가챠에서 교환 이야기를 활발하게 나눌수록, 선물을 만날 기회도 커져요.**

- 최종 응모 버튼을 누르면 **중계 서버가** `/api/v1/trades/me?page=0&size=100`부터 끝 페이지까지 조회한다. 최초 20개만 저장하지 않으며 최대 10,000개를 허용한다. 각 글의 소유자 회원번호도 확인한다.
- 이름·인스타그램 외에 회원번호, 교환글 수·ID, 동의·접수 기록도 수집 항목에 고지한다.
- 조회 오류·로그인 변경·페이지 정보 불일치·다른 회원의 글·시간 초과가 발생하면 불완전한 목록을 제출하지 않는다. 중계 요청 제한 시간은 기본 45초, 브라우저 제출 대기 한도는 60초다.
- 전체 페이지 조회는 데이터베이스의 한 시점 스냅샷 트랜잭션이 아니다. 페이지 수·전체 개수·중복·소유자 불일치를 검사하지만 조회 도중의 모든 동시 변경을 완전히 고정하지는 못한다. 실제 저장 값은 제출 처리 중 API에서 조회한 결과이며, 엄밀한 한 시점 기준이 필요하면 별도 백엔드 계약이 필요하다.
- 응모 뒤 작성한 글을 반영하려면 다시 응모해야 한다. 시트가 이후 활동을 자동 수집하지 않는다.
- 추첨 알고리즘이나 게시글당 가중치는 구현하지 않았다. 공개 전 유효 활동·도배 제외 기준과 실제 추첨 방식을 팀에서 확정한다.

## 2. 서버 설정 확정

### Apps Script 속성

Apps Script 프로젝트 설정 → 스크립트 속성에서 값을 지정한다. 아래 다섯 개인정보 설정은 2026-11-16 운영자가 승인한 값이다. 속성을 저장하는 것만으로 중계 서버가 설치되거나 옛 웹 앱 배포가 새 코드로 바뀌지는 않는다.

| 속성                     | 입력 기준                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| `ACCEPTING`              | 준비 중 `false`, 모든 검증 후 `true`                                                            |
| `SPREADSHEET_ID`         | 사용자가 직접 만든 **가치가챠 앱 출시 이벤트 v2 응모** 시트의 ID                                |
| `EVENT_RELAY_SECRET`     | 중계 서버와 동일한 무작위 64자리 16진수 문자열. 공개·브라우저 주입 금지                         |
| `START_AT`               | `2026-11-10T00:00:00+09:00`. DEV도 같은 시각을 사용하며 실제 접수는 `ACCEPTING`으로 제어        |
| `END_AT`                 | `2026-11-28T00:00:00+09:00` — 11/27 하루 전체까지, 이 시각은 미포함                             |
| `PRIVACY_CONTROLLER`     | `가치가챠팀`                                                                                    |
| `PRIVACY_CONTACT`        | `Instagram @gachi__.gacha`                                                                      |
| `PRIVACY_PURPOSE`        | `이벤트 참여 조건·활동 확인, 중복 응모 관리, 추첨, 인스타그램 DM을 통한 당첨 안내 및 경품 전달` |
| `PRIVACY_RETENTION_DAYS` | `30` — 최대 이벤트 종료 후 30일. 경품 전달 완료 시 더 일찍 삭제                                 |
| `RULES_VERSION`          | `app-launch-2026-v2-20261116` — 목적·항목·기간 등 변경 시 새 식별자로 변경                      |
| `MAX_SUBMISSIONS`        | 서로 다른 회원 수 상한, 기본 1000, 허용 1~10000                                                 |
| `MAX_RECEIPTS`           | 기술 접수 이력 상한, 기본·최대 100000. 상한 시 `RECEIPT_CAPACITY_REACHED`로 거절                |

`PRIVACY_RETENTION_DAYS`는 **이벤트 종료 후** 최대 보관일수다. 30일은 운영자가 승인한 운영 기준이며 법이 일률적으로 정한 보관기간은 아니다. 경품 전달이 먼저 완료되면 30일을 기다리지 않고 지체 없이 삭제한다. 속성 변경은 자동 삭제 작업을 만들지 않으므로 5절의 삭제 운영을 함께 수행한다.

처리 주체·문의·목적·수집 항목·보관기간은 메타데이터를 통해 응모 폼의 **개인정보 수집·이용 내용 보기**에 표시된다. 동의문에는 다음도 안내한다.

- 수집 항목: 이름, 인스타그램 ID, 회원번호, 응모 시점에 작성한 교환글 전체 ID와 개수, 동의 및 접수 기록. 전화번호·사연·사진은 받지 않는다.
- 동의 거부 시 이벤트에 응모할 수 없지만 다른 서비스 기능에는 영향이 없다.
- Google 스프레드시트에 저장하며 처리위탁·국외 이전 사항은 `/privacy`에서 확인할 수 있다. 방침 링크는 입력 중인 폼을 잃지 않도록 새 창으로 연다.
- `RULES_VERSION`은 화면 설명이 아니라 제출·접수 기록에 남겨 적용한 동의문을 구별한다.

schema3 메타데이터는 `authentication: 'server-verified'`와 로그인 회원번호·서버에서 조회한 본인 교환글을 안내한다. 이 표시는 실제 운영 설치와 검증을 대신하지 않는다. 승인 문구·개인정보처리방침·수신부 계약이 서로 일치하는지 확인한 후 공개한다. Google 보관·이전 및 동의 범위도 담당자가 검토하며, 이 문서나 코드만으로 법적 적합성을 보장하지 않는다.

접수 이력 상한에 도달했다고 진행 중 이력을 삭제해 공간을 만들면 과거 UUID 보호가 깨진다. 접수를 중단하고 운영 방식을 조정한다. 정책·일정 변경 시 이미 접수된 동의와 삭제 예정일도 함께 검토한다.

빈 정책·잘못된 일정·미설정 저장소는 서버가 접수를 거절한다. 유효하지 않은 메타데이터를 받은 프론트엔드도 폼 활성화를 막는다.

### 프론트엔드 인증 중계 서버 환경변수

예제는 `frontend/scripts/launch-event-relay/environment.example`에 있다. 실제 값은 DEV EC2의 **root 소유·권한 0600인 `/etc/gachi-launch-event-relay.env`**에서 관리한다. 이 파일은 저장소에 올리지 않는다.

| 환경변수             | DEV 기준 값 / 용도                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------- |
| `FRONTEND_ORIGIN`    | `https://dev.gachigacha.kro.kr` — POST를 허용할 웹 출처                                                       |
| `API_ORIGIN`         | `https://dev.gachigacha.kro.kr` — 기존 `/api` 역방향 프록시로 인증 API 호출. 관리자가 확인한 고정 주소만 사용 |
| `GAS_URL`            | schema3로 배포한 `https://script.google.com/macros/s/배포ID/exec`                                             |
| `EVENT_RELAY_SECRET` | Apps Script 속성과 대소문자까지 동일한 64자리 16진수 문자열                                                   |
| `PORT`               | 기본 `3101`. 서버는 `127.0.0.1`에서만 수신                                                                    |
| `MAX_CONCURRENT`     | 기본 `4`, 허용 `1~8`. 초과 시 `BUSY`로 거절                                                                   |
| `REQUEST_TIMEOUT_MS` | 기본 `45000`, 허용 `1000~60000`. API 조회부터 Google 응답까지 한 요청의 제한                                  |

`EVENT_RELAY_SECRET`은 안전한 난수로 생성한 32바이트를 64자리 16진수로 표현한다. **HMAC 계산에서는 그 64자리 문자열 자체를 UTF-8 키로 사용하며 hex 바이트로 다시 디코딩하지 않는다.** 양쪽에 완전히 같은 값을 직접 설정한다. GitHub 프론트엔드 Environment variables, `.env` 빌드 입력, 브라우저 번들, 채팅, PR, 명령 출력에 넣지 않는다. 유출·교체 시 먼저 접수를 닫고 양쪽 값을 함께 교체한 뒤 검증한다. 새 키로 전환하면 이전 키의 서명은 거절된다.

기존 인증 API를 재사용할 뿐 백엔드 프로젝트·공통 설정을 바꾸지 않는다. 회원 확인용 토큰을 받는 `API_ORIGIN`을 임의의 외부 호스트로 설정해서는 안 된다. DEV와 PROD는 서버 설정·비밀키·Google 배포·저장소를 각각 분리하며 이번 설치는 DEV만 수행한다.

## 3. 웹 앱 배포와 개발 환경 연결

### DEV 연결 순서 — 검증 완료 전에는 접수 닫힘 유지

1. 앞 절에 따라 시트·schema3 헤더·승인 정책·서명 비밀키를 준비하고 `ACCEPTING=false`인지 확인한다. 사용자 시트를 새로 만드는 `setupLaunchEventStorage()`는 다시 실행하지 않는다.
2. Apps Script에서 schema3 코드의 새 웹 앱 배포를 만든다. 실행자는 관리 계정, 접근은 중계 서버가 Google 로그인 없이 호출할 수 있는 범위로 설정한다. 외부 호출이 가능해도 POST는 HMAC 검증을 통과해야 한다. 조직 정책이 허용하지 않으면 인증 우회를 하지 않는다.
3. `/macros/s/.../exec`를 중계 서버의 `GAS_URL`에 설정한다. `/dev`는 허용하지 않는다. 같은 시트에 쓰던 서명 없는 옛 배포를 보관 처리하고 호출이 중단됐는지 확인한다.
4. DEV EC2에서 `server.mjs`와 고정 Node.js 실행 파일을 `/opt/gachi-launch-event-relay/`에 설치한다. 둘 다 root 소유이며 서비스 사용자가 수정할 수 없게 한다. CI가 교체할 수 있는 Actions runner의 Node 캐시 경로를 상시 서비스 실행 파일로 사용하지 않는다. 실제 설치할 Node 버전·아키텍처를 서버 환경에 맞게 확인한다.
5. `gachi-launch-event-relay.service.example`을 검토해 별도 systemd 서비스로 설치한다. 예제는 `DynamicUser`, 파일시스템 읽기 전용 등의 격리를 사용하며 환경 파일은 `/etc/gachi-launch-event-relay.env`를 읽는다. 기존 Nginx·runner·백엔드 서비스 파일을 덮어쓰지 않는다.
6. `nginx-location.conf.example`의 **정확히 일치하는 `location = /event-api/launch-event`만 DEV HTTPS server 블록 안에 추가**한다. 기존 정적 페이지, `/api` 프록시, 인증서 설정은 유지한다. `nginx -t` 통과 후에만 설정을 적용한다. 중계 포트 3101을 외부에 공개할 필요는 없다.
7. `GET /event-api/launch-event`가 schema3·`authentication: 'server-verified'`·승인 정책·`accepting:false`를 반환하는지 확인한다. 비밀키·토큰·시트 데이터가 응답에 없는지도 확인한다. 서비스가 실행됐다는 것만으로 접수 성공으로 판단하지 않는다.
8. GitHub의 **개발 환경** 변수에 아래 값을 저장하고 현재 변경을 포함한 DEV를 빌드·배포한다. 먼저 배너·로그인 복귀·닫힌 접수 화면을 확인한다. 실제 쓰기 검증은 아래 체크리스트에 따라 테스트 계정·별도 DEV 시트로 수행한다. 그 테스트를 수행하는 동안에만 담당자가 `ACCEPTING=true`로 전환하고, 실패하거나 설정이 미완료이면 다시 닫는다.

위 파일은 설치 **예제**이며 저장소 변경만으로 EC2에 설치되지 않는다. Nginx 예제는 요청 본문을 16KiB로 제한하고 필요한 헤더만 중계하며, 애매하게 끝난 POST를 자동 재전송하지 않는다. 실제 서버 설정·systemd 상태·기존 웹/API 정상 응답까지 확인해야 한다.

```text
EVENT_APPLICATION_CAMPAIGN_ID=app-launch-2026
EVENT_APPLICATION_ENDPOINT=/event-api/launch-event
EVENT_APPLICATION_BANNER_START_AT=2026-11-16T00:00:00+09:00
EVENT_APPLICATION_START_AT=2026-11-10T00:00:00+09:00
EVENT_APPLICATION_END_AT=2026-11-28T00:00:00+09:00
EVENT_APPLICATION_ENABLED=true
```

GitHub 경로: 저장소 → Settings → Environments → **frontend-development** → Environment variables. 운영은 별도 **frontend-production**이다. **브라우저 endpoint는 위 상대경로로 고정하며 Google URL이나 다른 출처 URL을 넣지 않는다.** `GAS_URL`과 서명 비밀키는 서버 전용 설정이다. 배너만 미리 볼 때 endpoint를 비워두면 실제 폼은 열리지 않는다. 운영 시작일의 기준은 11/10이지만 이번 작업에서 운영 설정을 변경하지 않는다.

**GitHub 변수 저장만으로 이미 배포된 화면이 바뀌지는 않는다.** Webpack이 빌드 때 값을 주입하므로 변경 후 해당 환경을 다시 빌드·배포한다. 현재 배포하고 싶은 최신 커밋의 배포 작업을 재실행해야 하며, 오래된 실행을 재실행하면 코드도 과거 버전으로 배포할 수 있다. 웹 및 같은 원격 웹 주소를 여는 WebView는 새 페이지를 로드하면 적용된다. 이미 열린 앱 화면은 새로고침/재진입이 필요할 수 있다. 웹 콘텐츠 변경만으로 네이티브 재빌드가 필요하지는 않지만 앱 심사·네이티브 변경과는 별개다.

설정된 종료 시각에는 추가 배포 없이 배너가 숨겨진다. 열린 화면은 약 30초 간격 및 화면 복귀 때 재검사한다. 사용자가 기기 시계를 조작할 수 있으므로 접수 마감은 Apps Script의 서버 시각으로도 강제한다.

응모 시작·종료 시각을 바꿀 때는 GitHub 변수와 Apps Script `START_AT`/`END_AT`를 함께 맞춘다. 일정이 다르면 폼을 열지 않는다. 긴급 접수 중단은 **Apps Script `ACCEPTING=false`**로 즉시 적용하며 기존에 열린 폼도 서버가 거절한다. 배너까지 즉시 원격 제어하려면 별도 런타임 설정 배포 방식이 필요하다. 현재 구현이 그 기능을 제공한다고 안내하지 않는다.

### 로컬에서 확인할 때

Webpack 개발 서버는 정확한 `/event-api/launch-event` 요청을 `http://127.0.0.1:3101`로 프록시한다. `changeOrigin:false`이므로 로컬 중계의 `FRONTEND_ORIGIN`은 실제 접속 주소인 `http://localhost:3000`으로 맞춘다. `API_ORIGIN`은 신뢰하는 **DEV API 주소**를 사용한다. 운영 계정·운영 접수 시트로 임의 테스트하지 않는다.

프론트엔드만 켜고 중계 서버를 실행하지 않으면 접수 연결은 실패한다. 로컬도 별도 비밀 환경 파일에서 relay 설정을 주입하며 브라우저용 `.env`에는 상대경로 외 Google 주소·비밀키를 넣지 않는다. 이 개발 프록시가 배포된 DEV Nginx 설정을 대신하지 않는다.

### 실제 접수를 열기 전 필수 검증

- 화면의 로그인 검사와 별개로 중계 서버가 인증된 요청자의 회원번호·글 소유권을 검증하는지 확인한다. 토큰 없음·만료·다른 회원의 `expectedMemberId`·본문에 임의로 추가한 `memberId`/`tradeIds`는 거절해야 한다.
- 공개 Apps Script로 보내는 서명 없는 요청·내용을 변조한 요청·5분 이상 지난 서명·틀린 키의 요청은 거절해야 한다. 옛 unsigned 배포 URL로도 저장할 수 없는지 확인한다.
- 별도 테스트 프로젝트/시트에 테스트 계정·입력으로 GET·POST를 수행한다.
- Android 웹뷰/Chrome, iOS 웹뷰/Safari에서 같은 출처 endpoint의 GET·POST와 로그인 복귀를 확인한다. 브라우저는 Google을 직접 호출하지 않지만, 중계 서버의 Google 리다이렉트 처리·조직 접근 정책·실기기 동작은 모의 테스트만으로 보장하지 않는다. 로그인 후 `apply=1` 복귀가 자동 제출로 이어져서는 안 된다.
- 이름·인스타그램·회원번호·모든 페이지의 글 ID·동의 버전이 정확한 열에 저장되는지 확인한다. `@`와 대소문자는 정규화한다.
- 같은 회원으로 글 추가 후 재응모하면 새 행이 아니라 최신 1행으로 갱신되는지 확인한다.
- 같은 UUID·같은 내용 재시도는 한 행과 같은 영수증을 반환한다. 같은 UUID·다른 내용은 거절한다.
- 오래된 요청을 뒤늦게 재시도해도 더 최신의 응모 정보를 덮어쓰지 않는지 확인한다.
- 마감 직전 부분 저장의 경우 두 탭을 담당자가 대조한다. GAS에는 동일 UUID·동일 해시 요청을 원래 보관기한 안에서 확인·복구하는 장치가 있지만, 현재 웹 폼과 중계 서버는 접수 중단·마감 뒤 요청을 먼저 막는다. 일반 브라우저 재시도로 마감 후 자동 복구된다고 안내하지 않는다.
- HTML 로그인 페이지·빈 응답·잘못된 캠페인·마감·동의 누락·정책 버전 변경은 완료 화면으로 넘어가지 않는다.
- 실패·시간 초과 시 입력을 유지하고 완료 화면으로 넘어가지 않는다. 서버에는 저장됐지만 응답만 못 받은 경우가 있을 수 있다. 재시도 시 서버가 본인 글을 다시 조회하므로 글 목록이 달라지면 기존 접수ID와의 충돌 여부도 확인한다. 충돌을 성공으로 바꾸거나 기록을 지워 우회하지 않는다.
- 검증을 통과한 DEV 연결만 활성화한다. 운영 저장소·운영 EC2·운영 GitHub 설정은 별도 승인과 분리된 검증 후에 적용한다. 서버 일정과 프론트엔드 일정이 다르면 접수는 열리지 않는다.

공개 Apps Script URL에는 유효하지 않은 직접 요청도 들어올 수 있다. HMAC은 신뢰하는 중계 서버가 검증한 본문임을 확인하는 장치이며 Google 실행 할당량 소모 자체를 막지는 않는다. 중계의 동시성 제한·본문 제한·출처 검사는 완전한 봇 방지나 회원별 요청 제한을 대신하지 않는다. 실제 공격·할당량 부족 시 먼저 접수를 닫고 운영 방식을 점검한다. 오류 로그에 요청 본문·Authorization·이름·인스타그램·비밀키를 추가하지 않는다.

### 연결을 위해 전달할 것

- 새 웹 앱 **`/exec` URL**. `/dev` 또는 시트 공유 URL이 아니다.
- 확정한 처리 주체, 문의 채널, 목적, 종료 후 보관일수, 동의문 버전.
- DEV/운영의 응모 시작 시각. 준비 확인 전에는 `ACCEPTING=false` 유지.
- 실제 서버 설치 여부와 GET 메타데이터의 설정 완료/닫힘 상태. 출력은 개인정보·비밀키 없이 요약한다.
- 액세스 토큰, Google 로그인 정보, **`EVENT_RELAY_SECRET`**, 실제 응모자 명단은 전달하지 않는다. 비밀키는 관리자가 양쪽 비공개 설정에 직접 넣으며 스프레드시트를 공개 공유할 필요도 없다.

## 4. 전송 계약

### 브라우저 → 같은 출처의 인증 중계 서버

- 주소: `/event-api/launch-event`만 사용한다. 메타데이터 GET은 로그인 없이 제공하고 POST는 `Authorization: Bearer …`가 필요하다.
- POST 형식: `application/json`, 최대 16KiB. 허용 필드는 `eventId, schemaVersion, submissionId, expectedMemberId, name, instagramId, privacyConsent, rulesConsent, rulesVersion`이다.
- `schemaVersion`은 `3`이다. `expectedMemberId`는 화면에서 확인한 계정과 서버 인증 결과를 대조하는 값일 뿐이며 서버가 저장할 ID를 지정하지 않는다. `memberId`, `tradeIds`, 토큰을 담은 본문 필드 등 허용 목록 밖 값은 거절한다.
- 중계 서버는 지정한 출처의 POST만 허용하고, 고정된 기존 API에서 회원과 교환글을 확인한다. API 오류·정책 변경·소유자 불일치·불완전한 페이지 결과를 Google 제출로 넘기지 않는다.

### 인증 중계 서버 → Apps Script

중계 서버가 생성하는 내부 접수 본문은 `eventId, schemaVersion, submissionId, memberId, name, instagramId, tradeIds, privacyConsent, rulesConsent, rulesVersion`만 포함한다. 여기의 `memberId`와 `tradeIds`는 **서버 검증 결과**다. 액세스 토큰·리프레시 토큰·쿠키는 들어가지 않는다.

이 본문을 JSON 문자열 `payload`로 만든 후 다음 봉투만 `text/plain;charset=UTF-8` JSON으로 전송한다.

```text
payload   = 검증한 접수 본문의 JSON 문자열
timestamp = Unix epoch 기준 현재 시각 (정수 밀리초)
signature = HMAC-SHA256(EVENT_RELAY_SECRET, `${timestamp}\n${payload}`)
            결과를 소문자 64자리 hex 문자열로 표현

전송 본문 = JSON.stringify({ payload, timestamp, signature })
```

양쪽 모두 64자리 비밀 문자열을 **UTF-8 키 그대로** 사용한다. Apps Script는 서명을 확인하기 전에 본문을 신뢰하지 않으며 서버 시각과 ±5분을 초과하는 서명도 거절한다. 캠페인·v3 스키마·동의·정책 버전·기간·문자 길이·중복 없는 양의 정수 글 ID·전체 봉투 256KiB 상한도 검사한다. 회원 인증 자체는 중계 서버와 기존 인증 API의 책임이며 GAS가 JWT를 검증하는 구조가 아니다.

Google ContentService의 결과 리다이렉트는 중계 서버가 제한된 `script.googleusercontent.com` HTTPS 주소로 한 번만 GET한다. 그 GET에 원래 POST 본문이나 Authorization을 다시 붙이지 않는다. 응답이 HTML·잘못된 JSON·다른 캠페인·다른 접수ID이면 성공으로 취급하지 않는다.

성공 응답:

```json
{
  "ok": true,
  "eventId": "app-launch-2026",
  "submissionId": "019ab251-394e-4a77-9c21-1221ea123456",
  "receivedAt": "2026-11-12T00:00:00.000Z"
}
```

`ok`만 있는 기존 응답은 성공으로 인정하지 않는다. 응답의 접수ID·이벤트ID·시각을 확인한 후 완료 화면을 표시한다. 이것은 **회원·본인 글을 확인한 접수의 영수증**이며 앱 설치·전체 참여 자격·당첨 확인은 아니다.

Apps Script는 잠금 안에서 접수이력을 먼저 기록한 다음 최신 응모 행을 갱신한다. 같은 UUID·같은 전체 내용은 같은 영수증을 반환하고, 다른 내용이면 충돌로 거절한다. 과거 UUID 재시도가 더 최신 응모를 덮어쓰지 않게 한다. 두 탭이 데이터베이스 트랜잭션인 것은 아니므로 부분 실패가 반복되면 접수를 닫고 담당자가 대조한다.

GAS 내부에는 중단·마감·정책 변경 후에도 기존 UUID와 원래 해시가 같으면 원래 보관기한 안에서 확인·복구하는 경로가 있다. 다만 일반 웹 폼과 중계 서버는 접수 가능 여부를 먼저 검사하며, 별도의 운영자 복구 API를 제공하지 않는다. 따라서 이 내부 장치를 근거로 사용자에게 마감 후 재시도를 약속하거나 접수를 임의 재개하지 않는다.

## 5. 보관기간 종료와 정리

1. 접수 종료 시 `ACCEPTING=false`로 닫고 운영 담당자와 삭제 확인 일정을 기록한다.
2. 경품 전달 완료 후에는 **최대 30일을 기다리지 않는다.** 담당자가 대상 이벤트를 확인하고 응모정보와 연결된 접수이력을 함께 조기 삭제한다. 현재 코드에는 경품 전달 완료를 감지하는 기능이나 조기 삭제 자동화가 없다. 전체 시트나 다른 이벤트 자료를 일괄 삭제하지 않는다.
3. 최대 보관기한 확인에는 `cleanupExpiredEntries()`를 실행한다. 인자를 생략하면 만료 대상 **개수만** 반환한다. 이 함수는 `삭제예정일`이 지난 행만 찾으므로 2번의 조기 삭제를 대신하지 못한다.
4. 담당자가 보관 기준과 대상 수를 확인한 뒤 `cleanupExpiredEntries(false)`를 실행한다. 이벤트 종료 후 보관기한이 지난 해당 이벤트의 응모 행과 접수이력만 삭제한다. 접수 기간 중 이력은 삭제하지 않는다.
5. 시트 버전 기록, 다운로드한 CSV·복사본 등 잔존 자료도 승인된 보관 정책에 따라 정리한다. 행 삭제는 모든 사본의 영구 삭제를 보장하지 않는다.
6. 저장소 오류가 발견되면 출처를 확인하기 전에 광범위 삭제나 재실행으로 우회하지 않는다.

`PRIVACY_RETENTION_DAYS=30`을 저장해도 자동 삭제 트리거가 설치되지는 않는다. 운영자는 조기 삭제·최대 보관기한 일정을 등록하고 실행 결과를 확인해야 한다. 마지막에는 웹 앱 배포 중지·접근 권한 회수 및 필요하지 않은 보관 사본을 점검한다.

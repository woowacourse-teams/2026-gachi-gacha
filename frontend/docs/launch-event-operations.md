# 앱 출시 이벤트 접수 운영

## 현재 상태

이 문서는 `app-launch-2026` 전용 접수 계약이다. 기존 인기 굿즈 이벤트의 시트·스크립트·응답 형식과 호환되지 않는다. **코드 추가만으로 Google 시트, Drive 폴더 또는 웹 앱이 생성되거나 접수가 활성화되지는 않는다.**

- 경품: 4종 각 2개, 총 8명에게 1인 1개 무작위 증정. 중복 당첨 제외.
- 입력: 이름, 휴대폰 번호, 사연, 선택 사진 최대 3장.
- 임시 일정: 11월 24일 마감, 11월 27일 발표. 정확한 시작 시각·마감 시각·발표 방법은 운영자가 확정해야 한다.
- 미확정: 개인정보 처리 주체, 문의 연락처, 수집 목적의 확정 문구, 보관기간, 동의 문구 버전.
- 위 항목 및 실제 브라우저 전송 검증 전에는 `EVENT_APPLICATION_ENABLED=false`, `ACCEPTING=false`를 유지한다.

기존 서비스 로그인은 프론트엔드 진입 조건이다. Google Apps Script는 가치가챠 세션을 검증하지 않는다. 제출된 회원번호는 **자가 신고 값**이며 회원 인증 완료나 참여 자격 충족을 보장하지 않는다. 앱 설치·게시글 작성·당첨 중복은 운영자가 별도로 검증해야 한다. 인증된 회원만 엄격히 접수하려면 별도 서버 검증 계약이 필요하다. 이 구현은 운영 액세스 토큰·리프레시 토큰·쿠키를 Google로 보내지 않는다.

## 1. 별도 저장소 준비

화면의 경로·대체 텍스트는 `src/features/launchEvent/launchEventContent.ts`에서 교체한다. 실제 화면용 이미지는 원본 비율을 유지하고, 경품 안내는 지연 로드한다. 글자가 들어간 이미지의 핵심 내용은 주변 HTML로도 제공한다.

상품 이미지의 웹사이트 재사용 허락은 확인되지 않았다. 사용자 요청에 따라 상품 식별용으로 연결했으며, 다른 사이트의 사용 사례·출처 표시·비협찬 안내가 이용 허락을 대신하거나 저작권 위험을 없애지는 않는다. 별도로 허락받은 이미지 또는 직접 촬영한 사진으로 교체할 수 있다. 원본에 포함된 표시는 임의로 제거하지 않았다.

### 이전 이벤트 링크

기존 마이페이지 진입 메뉴는 제거하고 `/events/popular-goods`는 새 상세 주소 `/events/app-launch`로 이동한다. 과거 폼이 새로운 Apps Script에 이전 필드를 보내지 않도록 실제 라우팅에서 분리했다. 기존 시트·스크립트는 수정하지 않았다.

1. 팀이 관리하는 Google 계정으로 **새 Apps Script 프로젝트**를 만든다. 기존 이벤트 프로젝트는 수정하지 않는다.
2. `frontend/scripts/launch-event-apps-script/Code.gs`를 복사한다.
3. `setupLaunchEventStorage()`를 한 번 실행하고 필요한 Google 권한을 확인한다.
4. 스크립트 속성에서 `SPREADSHEET_ID`, `PHOTO_FOLDER_ID`가 만들어졌는지 확인한다. 재실행 방지 검사가 있으므로 기존 ID를 지워 반복 실행하지 않는다.
5. 생성된 시트와 사진 폴더는 비공개다. 링크 공개를 켜지 말고 실제 담당자에게만 필요한 권한을 부여한다. 워크스페이스 정책·상속 권한도 확인한다.

설정 함수가 중간에 실패했다면 Google Drive에 일부 자원이 생겼을 수 있다. 자동 재실행하지 말고 생성 내역과 스크립트 속성을 먼저 확인한다. 실제 POST에서도 시트와 사진 폴더의 링크 공유가 비공개인지 검사하지만, 담당자별 직접 공유·조직 권한까지 자동 감사하지는 않는다.

자동 생성 열:

| 열                                        | 용도                                           |
| ----------------------------------------- | ---------------------------------------------- |
| 접수일시 / 이벤트ID / 접수ID              | 서버 접수 시각, 캠페인, UUID 재시도 식별       |
| 자가신고회원ID / 이름 / 연락처 / 응모사연 | 운영자 확인용 입력                             |
| 개인정보동의 / 유의사항동의 / 약관버전    | 접수 당시 동의 기록                            |
| 사진파일ID                                | 비공개 Drive 파일 ID 배열. 공개 URL 아님       |
| 요청해시                                  | 같은 UUID로 다른 내용을 보내는 경우 거절       |
| 삭제예정일                                | 접수 시각 + 설정 보관일수                      |
| 운영검증상태                              | 기본 `미검증`. 운영자가 자격·중복 확인 후 기록 |

헤더 이름·순서를 변경하면 접수가 중단된다. 회원번호·전화번호 등은 텍스트로 저장하고 수식 시작 문자를 방어한다. 개인정보가 들어 있는 열이나 파일을 GitHub 이슈·스크린샷·공개 문서에 올리지 않는다.

## 2. 서버 설정 확정

Apps Script 프로젝트 설정 → 스크립트 속성에서 값을 지정한다. 개인 계정의 비공개 주소를 임의로 넣거나 예시 정책을 실제 동의문으로 사용하지 않는다.

| 속성                     | 입력 기준                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| `ACCEPTING`              | 준비 중 `false`, 모든 검증 후 `true`                                                     |
| `START_AT`               | 확정 시작 시각, 시간대 포함 ISO 8601                                                     |
| `END_AT`                 | 종료 시각 **미포함**. 예: 11/24 하루 전체 마감이라면 확정 후 `2026-11-25T00:00:00+09:00` |
| `PRIVACY_CONTROLLER`     | 실제 처리 주체 이름                                                                      |
| `PRIVACY_CONTACT`        | 실제 이용 가능한 문의 채널                                                               |
| `PRIVACY_PURPOSE`        | 실제 수집·이용 목적                                                                      |
| `PRIVACY_RETENTION_DAYS` | 실제 보관일수, 정수 1~365. 법적 적합성을 자동 보장하는 값이 아님                         |
| `RULES_VERSION`          | 확정된 동의문 식별자. 목적·항목·기간 등 변경 시 반드시 변경                              |
| `MAX_SUBMISSIONS`        | 총 접수 상한, 기본 1000, 허용 1~10000                                                    |

`PRIVACY_RETENTION_DAYS`는 접수일 기준이다. 당첨 발표일 기준 보관 등 다른 정책이라면 코드와 문구를 함께 바꿔야 한다. 선택 사진의 필요성, 사진 속 개인정보와 위치정보(EXIF), Google 보관·이전 및 동의 범위는 담당자가 검토한다. 현재 서버는 이미지 형식 서명과 크기를 검사하지만 EXIF 제거·악성 콘텐츠 검사를 수행하지 않는다.

빈 정책·잘못된 일정·미설정 저장소는 서버가 접수를 거절한다. 유효하지 않은 메타데이터를 받은 프론트엔드도 폼 활성화를 막는다.

## 3. 웹 앱 배포와 개발 환경 연결

1. 새 웹 앱 배포를 만든다. 실행자는 관리 계정, 접근은 외부 브라우저가 로그인 없이 호출할 수 있는 범위로 설정한다. 조직 정책이 허용하지 않으면 인증 우회를 하지 말고 연결 방식을 다시 정한다.
2. `/macros/s/.../exec` 주소를 사용한다. 테스트용 `/dev` 주소는 허용하지 않는다.
3. GitHub의 **개발 환경** 변수에 아래 값을 저장한다. 운영 환경 변수는 별도 승인 없이 바꾸지 않는다.

```text
EVENT_APPLICATION_CAMPAIGN_ID=app-launch-2026
EVENT_APPLICATION_ENDPOINT=https://script.google.com/macros/s/배포ID/exec
EVENT_APPLICATION_START_AT=서버와 같은 확정 시작 시각
EVENT_APPLICATION_END_AT=서버와 같은 확정 종료 시각
EVENT_APPLICATION_ENABLED=false
```

환경변수는 빌드 시 반영된다. GitHub 변수만 바꾸고 기존 번들이 바뀐다고 가정하지 않는다. 접수 긴급 중단은 서버 `ACCEPTING=false`로 즉시 수행한다.

### 실제 접수를 열기 전 필수 검증

- 별도 테스트 프로젝트/시트에 테스트 정보로 GET·POST를 수행한다. 테스트 계정·사진만 사용한다.
- Android 웹뷰/Chrome, iOS 웹뷰/Safari에서 메타데이터 GET과 POST 응답을 실제로 읽는지 확인한다. Apps Script 리다이렉트·CORS·조직 접근 정책은 단위 테스트가 보장하지 않는다.
- 이름·연락처·사연·동의 버전이 정확한 열에 저장되고, 전화번호 앞 `0`이 보존되는지 확인한다.
- 사진은 지정된 비공개 폴더에 저장되고 익명 URL로 접근되지 않는지 확인한다.
- 같은 UUID·같은 내용 재시도는 한 행과 같은 영수증을 반환한다. 같은 UUID·다른 내용은 거절한다.
- HTML 로그인 페이지·빈 응답·잘못된 캠페인·마감·동의 누락·정책 버전 변경은 완료 화면으로 넘어가지 않는다.
- 실패·시간 초과 시 입력을 유지하고 이전 접수ID로 재시도한다. 서버에는 저장됐지만 응답만 못 받은 경우가 있을 수 있다.
- 준비 완료 후에만 새 운영 저장소 설정, GitHub 활성화 및 재빌드, 서버 `ACCEPTING=true`를 진행한다. 서버 일정과 프론트엔드 일정이 다르면 접수는 열리지 않는다.

공개 Apps Script URL에는 로그인하지 않은 직접 요청도 들어올 수 있다. 접수 상한과 잠금은 중복·동시 쓰기를 줄이는 장치이며 봇 방지나 회원 인증을 대신하지 않는다. 실제 공격·할당량 부족 시 먼저 접수를 닫고 서버 검증/속도 제한 도입을 검토한다.

## 4. 전송 계약

요청은 `text/plain;charset=UTF-8` JSON이며 허용 필드만 보낸다. 사진의 `data`는 data URL 접두사 없는 base64다. 서버는 캠페인·스키마·동의·정책 버전·기간·문자 길이·사진 MIME/파일 서명·크기(각 5MiB, 3장)·본문 상한(22MiB)을 검증한다.

성공 응답:

```json
{
  "ok": true,
  "eventId": "app-launch-2026",
  "submissionId": "019ab251-394e-4a77-9c21-1221ea123456",
  "receivedAt": "2026-11-12T00:00:00.000Z"
}
```

`ok`만 있는 기존 응답은 성공으로 인정하지 않는다. 응답의 접수ID·이벤트ID·시각을 확인한 후 완료 화면을 표시한다. 이것은 **접수 확인**이며 자격 검증·당첨 확인은 아니다. Google 시트와 Drive는 단일 트랜잭션이 아니므로 오류가 반복되면 접수를 닫고 행과 파일을 담당자가 대조한다.

## 5. 보관기간 종료와 정리

1. `ACCEPTING=false`로 닫는다.
2. `cleanupExpiredEntries()`를 실행한다. 인자를 생략하면 만료 대상 **개수만** 반환한다.
3. 담당자가 보관 기준과 대상 수를 확인한 뒤 `cleanupExpiredEntries(false)`를 실행한다. 만료된 응모 행은 삭제하며, 해당 이벤트 폴더·접수ID 파일명까지 검증한 사진만 Drive 휴지통으로 옮긴다.
4. Drive 휴지통 파일, 시트 버전 기록, 다운로드한 CSV·복사본 등 잔존 자료도 확정된 보관 정책에 따라 정리한다. 휴지통 이동과 행 삭제는 모든 사본의 영구 삭제를 보장하지 않는다.
5. 잘못된 행/파일 관계가 발견되면 정리가 중단된다. 출처를 확인하기 전에 광범위 삭제나 재실행으로 우회하지 않는다.

자동 삭제 트리거는 코드만으로 설치되지 않는다. 운영자는 삭제 일정을 등록하고 결과를 확인해야 한다. 마지막에는 웹 앱 배포 중지·접근 권한 회수 및 필요하지 않은 보관 사본을 점검한다.

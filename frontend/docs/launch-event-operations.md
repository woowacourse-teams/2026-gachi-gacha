# 앱 출시 이벤트 접수 운영

## 현재 상태

이 문서는 `app-launch-2026`, **`schemaVersion: 4`, `authentication: 'client-reported'`** 접수 계약이다. 사용자 요청에 따라 별도 중계 서버 없이 **브라우저에서 Google Apps Script 웹 앱으로 직접 제출**한다. 회원번호를 사용자에게 입력받지는 않지만, GAS가 받은 회원번호·교환글 ID의 진위를 서버에서 검증하는 구조는 아니다.

**로그인한 사용자에게 폼을 보여주는 것과 접수 서버가 로그인 회원을 인증하는 것은 다르다.** 정상 웹·앱에서는 기존 로그인 상태와 인증 API로 본인의 정보를 수집한다. 그러나 공개 `/exec` 주소로 직접 요청을 만들면 다른 회원번호·글 ID도 보낼 수 있다. 같은 회원번호의 최신 행을 갱신하므로 **다른 사람의 회원번호를 도용한 요청이 그 사람의 응모 정보를 덮어쓸 위험도 있다.** 입력 형식 검사·UUID 중복 방어는 이 위험을 해결하지 않는다. 운영자는 이 한계를 전제로 참여 조건과 당첨 대상을 확인한다.

코드 병합만으로 Google 코드·배포 버전이 바뀌거나 접수가 활성화되지는 않는다. **기존 Apps Script를 새 버전으로 배포하고 실제 브라우저→시트 검증이 끝날 때까지 `ACCEPTING=false`를 유지한다.** 이번 DEV 연결에는 EC2·Nginx 설치나 변경이 필요하지 않다. `main`, 운영 환경 설정, Google의 실제 설정 변경을 이 문서 작성으로 완료했다고 간주하지 않는다.

- 경품: 4종 각 2개, 총 8명에게 1인 1개 무작위 증정. 중복 당첨 제외.
- 입력: 이름, 인스타그램 아이디. 전화번호·사연·사진은 받지 않는다.
- 최종 제출 때 브라우저가 로그인 회원번호와 현재 조회 가능한 본인의 모든 교환글 ID를 수집한다. 교환 상태 필터 없이 끝 페이지까지 조회하며, 삭제된 글은 복원할 수 없다.
- 같은 **전달 회원번호**로 다시 응모하면 최신 정보와 교환글 목록으로 1행을 갱신한다. 반복 클릭 횟수 자체가 추첨 기회를 늘리지는 않는다.
- 일정: 안내·응모 시작 11/10, 최종 마감 11/27. 사용자가 정정한 시작일을 적용한다. 한국 시간 11/10 00:00부터 11/27 23:59까지이며, 종료 값은 **11/28 00:00 미포함**이다.
- 당첨자는 인스타그램 DM으로 개별 안내한다. 이전 시안의 11/27 발표일은 사용하지 않는다. 발표 시각은 별도 확정한다.
- 승인한 개인정보 기준: 처리 주체 `가치가챠팀`, 문의 `Instagram @gachi__.gacha`, 아래의 수집 목적·항목 및 경품 전달 완료 후 지체 없이 삭제/최대 이벤트 종료 후 30일 보관.
- 배너 공개와 접수 가능 여부는 별개다. DEV 배너는 미리 볼 수 있지만 저장소·정책·브라우저 검증 전에는 접수를 닫아 둔다.

### 로그인과 저장의 경계

```text
웹 / 같은 웹 주소를 여는 앱
  → 기존 AuthSession의 로그인 상태 확인
  → 기존 인증 API /api/v1/trades/me 전체 페이지 조회
  → 브라우저가 회원번호·글 ID와 입력·동의 내용을 구성
  → Google Apps Script /exec에 직접 제출 (토큰·쿠키 제외)
  → 형식·기간·동의·중복 검사
  → 비공개 응모 / 접수이력 시트 저장
     운영검증상태: 웹·Android 앱·iOS 앱·기기 미확인 앱 전달 / 참여 조건 확인 필요
                   (환경 미전달 구형 요청: 브라우저 전달 / 참여 조건 확인 필요)
```

- 비로그인 사용자는 **비활성화된 ‘로그인하고 응모해주세요!’ 버튼**과 안내를 본다. 이벤트에서 웹 로그인 화면을 강제로 열지 않는다. 각 앱/사이트의 기존 로그인 기능을 이용한 뒤 이벤트로 돌아온다. 로그인만으로 자동 응모하지 않는다. 과거에 만들어진 `?apply=1` 주소는 로그인·접수 가능 상태를 모두 확인한 경우에만 폼을 연다.
- 인증 확인 중에는 ‘로그인 확인 중…’, 로그인 후 Google 메타데이터 응답을 기다릴 때는 ‘접수 정보를 확인하고 있어요…’로 구분한다. Google 조회에는 네트워크 지연이 있을 수 있으며, 지연을 숨기려고 접수 기간·동의문 확인을 건너뛰거나 오래된 응답을 캐시하지 않는다.
- 폼 진입·조회·제출 과정에서 로그인 계정 변경을 검사한다. 회원번호는 로그인 정보에서 읽고 글 ID는 기존 인증 API에서 조회한다. 이 브라우저 검사는 정상 사용 중 잘못된 계정으로 접수하는 실수를 줄이지만 조작된 직접 요청을 차단하는 서버 인증은 아니다.
- 액세스 토큰은 기존 우리 서비스 인증 API 요청에만 사용한다. Google 요청의 헤더·본문·URL·시트에 액세스 토큰, 리프레시 토큰, 쿠키를 넣지 않는다.
- GAS는 JWT·회원 API·글 소유권·앱 설치를 확인하지 않는다. `authentication: 'client-reported'`는 이 제한을 나타내는 메타데이터이며 인증 성공의 증명이 아니다.
- `frontend/scripts/launch-event-relay/`의 중계 서버·systemd·Nginx 예제는 **이전 schema3 자료로 보존하지만 이번 직결 경로에서는 사용하지 않는다.** 설치·서비스 시작·중계 비밀키 설정을 할 필요가 없다. 기존 중계 설정이 있더라도 이 작업에서 임의로 삭제하거나 중지하지 않는다.

### 이전 이벤트 링크

기존 마이페이지 진입 메뉴는 제거하고 `/events/popular-goods`는 새 상세 주소 `/events/app-launch`로 이동한다. 과거 폼이 새로운 Apps Script에 이전 필드를 보내지 않도록 실제 라우팅에서 분리했다. 기존 인기 굿즈 이벤트 시트·스크립트는 수정하지 않는다.

### 이미 만든 시트는 재생성·재전환하지 않기

사용자는 **가치가챠 앱 출시 이벤트 v2 응모** 시트와 **응모 / 접수이력** 탭을 직접 만들었고 헤더 전환도 완료했다. 시트 제목의 `v2`와 전송 계약의 `schemaVersion: 4`는 별개다. **이번 작업에서는 `setupLaunchEventStorage()`와 `migrateEmptyLaunchEventStorageToVerified()`를 다시 실행하지 않는다.** v4는 전환된 v3 헤더를 그대로 사용한다.

1. 현재 시트의 **확장 프로그램 → Apps Script**에서 기존 프로젝트를 연다. 과거 인기 굿즈 이벤트 프로젝트와 혼동하지 않는다.
2. 스크립트 속성 `SPREADSHEET_ID`가 현재 시트 주소 `/spreadsheets/d/시트ID/edit`의 ID와 일치하는지 확인한다. 시트 공유 URL 전체를 넣지 않는다.
3. `ACCEPTING=false`를 유지하고 두 탭의 첫 행을 아래 계약과 대조한다. 기존 응모 데이터·접수이력을 지우거나 이름만 바꾸어 검증 완료로 처리하지 않는다.
4. 스프레드시트 링크 공개를 켜지 않고 실제 담당자에게만 필요한 권한을 부여한다. 워크스페이스 정책·공유 드라이브의 상속 권한도 확인한다. 사진 폴더는 필요하지 않다.

`setupLaunchEventStorage()`는 저장소가 전혀 없는 **별도 새 프로젝트**에서만 사용하는 생성 함수다. 현재 연결을 고치려고 기존 ID를 지우거나 반복 실행하지 않는다. 실기기 접수 테스트는 가능하면 별도 DEV 프로젝트·테스트 시트·테스트 계정을 사용한다. 실제 POST의 비공개 링크 공유 검사만으로 담당자별 직접 공유·조직 권한까지 감사되는 것은 아니다.

헤더 이름·순서를 변경하면 접수가 중단된다. 회원번호 등은 텍스트로 저장하고 수식 시작 문자를 방어한다. 개인정보가 들어 있는 행을 GitHub 이슈·스크린샷·공개 문서에 올리지 않는다. 접수 중에는 이력 행을 지우지 않는다.

### 기기 구분 추가 — 기존 데이터와 헤더 유지

기존 ‘브라우저 전달’은 **기기가 PC라는 뜻이 아니라, 서버에서 진위를 검증하지 않은 전달값이라는 뜻**이다. 이전 행만으로 Android/iOS 여부를 복원할 수 없으므로 소급 추정해서 수정하지 않는다.

- 새 `Code.gs`는 GET 응답에 `capabilities: { participationPlatform: true }`를 추가한다. 웹은 이 지원 표시가 있을 때만 POST에 `participationPlatform`을 추가한다. 구버전 GAS는 알 수 없는 필드를 거절하므로 지원 표시가 없으면 기존 payload를 유지한다.
- `schemaVersion: 4`, 두 탭의 열 제목·순서·기존 데이터는 그대로다. **setup/migrate 실행, 열 추가/삭제가 필요 없다.** 새 분류는 `운영검증상태`에 기록하며, 실제 회원/글/앱 설치 검증 완료라는 뜻이 아니다.
- 같은 회원의 새 UUID 응모는 최신 참여 환경으로 갱신한다. 같은 UUID로 참여 환경을 추가·변경하면 다른 내용의 재시도로 보고 거절하며, 과거 UUID 재전송은 최신 응모 정보를 덮어쓰지 않는다.
- 같은 프로젝트의 `Code.gs`를 교체하고 **배포 관리 → 수정 → 새 버전 → 배포**한다. `/exec` 응답에서 capability를 확인하고 이벤트 화면을 새로 열면 이후 응모부터 구분된다. 웹 코드 병합만으로 Google 코드는 갱신되지 않는다.
- 개인정보 안내에 ‘응모 환경(웹·Android 앱·iOS 앱·기기 미확인 앱)’이 포함된다. 운영자는 변경 동의문에 맞춰 `RULES_VERSION`을 새 값(예: `app-launch-2026-v4-platform-20261116`)으로 변경한다. 이전 동의/접수 기록은 바꾸지 않는다. 모델명·전체 User-Agent·기기 고유번호는 수집하지 않는다.

| 환경                    | 판별과 앱 빌드 필요 여부                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Android 앱              | 이미 있는 `data-gachigacha-native-platform="android"`를 우선 사용. 이 코드가 포함된 APK라면 새 APK 불필요                |
| iOS 앱                  | 같은 `ios` 표식 또는 기존 React Native WebView 브리지와 iOS 환경 조합 사용. 현재 iOS 앱 코드/실기기에서는 별도 확인 필요 |
| 모바일/PC 브라우저      | 앱 표식·브리지 없으면 `web`. Android Chrome과 iPhone Safari도 웹 참여                                                    |
| 브리지만 있고 OS 미확인 | `app-unknown`. 임의로 iOS나 웹으로 분류하지 않음                                                                         |

iOS 담당자는 앱 표식과 React Native 브리지가 모두 없다면 WKWebView의 문서 시작 스크립트에 아래 신호를 넣고 새 앱을 배포한다. 이미 React Native 브리지가 있는 앱은 먼저 기존 버전으로 확인한다. Android/iOS 코드는 서로 다른 값만 사용하므로 웹에서 하나의 판별 함수를 사용할 수 있다.

```js
// 앱에서 주입할 값: Android는 'android', iOS는 'ios'
// documentElement 생성 전일 수 있는 문서 시작 시점도 처리한다.
(() => {
  const mark = () => {
    document.documentElement.dataset.gachigachaNativePlatform = 'ios';
  };
  if (document.documentElement) mark();
  else document.addEventListener('DOMContentLoaded', mark, { once: true });
})();
```

이 표식은 앱이 제공하는 **클라이언트 참여 경로 정보**다. 조작 방지나 앱 설치 증명 수단으로 사용하지 않는다.

### 교환글 ID 열이 다섯 개인 이유

각 열은 ID 한 개가 아니라 **최대 2,000개짜리 JSON 배열**이다. 글 5개라면 목록1=`[3,7,10,45,55]`, 목록2~5=`[]`, 교환글수=`5`가 정상이다. 글 2,001개이면 목록1에 2,000개, 목록2에 1개가 들어간다. 합계는 비어 있지 않은 열 수가 아니라 전체 ID 개수이며 최대 10,000개다. 빈 배열은 오류·추가 가중치·5개 제한을 만들지 않는다.

웹은 `/trades/me`의 마지막 페이지까지 조회하고 합계가 제공되면 개수도 대조한다. 예전 `교환글수=1` 행의 원인은 행만으로 단정하지 않는다. 당시 계정의 조회 가능한 글이 하나였거나 이후 글을 추가했을 수 있다. 같은 로그인 계정의 내 글과 최신 응모 ID 목록을 비교한다. 삭제된 글과 응모 이후 새로 쓴 글은 이전 접수에 자동 추가되지 않는다.

### 참여 활동 안내와 수집 기준

화면 문구: **가치가챠에서 교환 이야기를 활발하게 나눌수록, 선물을 만날 기회도 커져요.**

- 최종 응모 버튼을 누르면 **브라우저가** `/api/v1/trades/me?page=0&size=100`부터 끝 페이지까지 조회한다. 최초 20개만 저장하지 않으며 최대 10,000개를 허용한다. 응답의 글 소유자 회원번호도 브라우저에서 대조한다.
- 이름·인스타그램 외에 회원번호, 교환글 수·ID, 응모 환경, 동의·접수 기록도 수집 항목에 고지한다. GAS에 도착한 회원번호·글 정보·응모 환경은 클라이언트 전달값이라는 점을 구분한다.
- 조회 오류·로그인 변경·페이지 정보 불일치·다른 회원의 글·시간 초과가 발견되면 정상 폼에서는 불완전한 목록을 제출하지 않는다. 이 동작은 직접 조작한 요청의 진위를 보장하지 않는다.
- 전체 페이지 조회는 데이터베이스의 한 시점 스냅샷 트랜잭션이 아니다. 조회 도중의 모든 동시 변경을 완전히 고정하지 못한다. 엄밀한 한 시점 기준이나 서버 검증이 필요하면 별도 서버 계약이 필요하다.
- 응모 뒤 작성한 글을 반영하려면 다시 응모해야 한다. 시트가 이후 활동을 자동 수집하지 않는다.
- 추첨 알고리즘이나 게시글당 가중치는 구현하지 않았다. 공개 전 유효 활동·도배 제외 기준과 실제 추첨 방식을 팀에서 확정한다. 앱 설치·본인 글·중복 당첨 여부도 별도 운영 확인 대상이다.

## 2. Apps Script 설정 확정

Apps Script **프로젝트 설정 → 스크립트 속성**에서 값을 지정한다. 아래 개인정보 처리 주체·문의·목적·보관 기준은 운영자가 승인한 내용이다. 수집 항목에는 브라우저 전달값이라는 설명을 함께 제공한다.

| 속성                     | 입력 기준                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| `ACCEPTING`              | 준비 중 `false`, 실제 DEV 접수 테스트 때 담당자가 `true`로 전환                                 |
| `SPREADSHEET_ID`         | 사용자가 직접 만든 **가치가챠 앱 출시 이벤트 v2 응모** 시트의 ID                                |
| `START_AT`               | `2026-11-10T00:00:00+09:00`                                                                     |
| `END_AT`                 | `2026-11-28T00:00:00+09:00` — 11/27 하루 전체까지, 이 시각은 미포함                             |
| `PRIVACY_CONTROLLER`     | `가치가챠팀`                                                                                    |
| `PRIVACY_CONTACT`        | `Instagram @gachi__.gacha`                                                                      |
| `PRIVACY_PURPOSE`        | `이벤트 참여 조건·활동 확인, 중복 응모 관리, 추첨, 인스타그램 DM을 통한 당첨 안내 및 경품 전달` |
| `PRIVACY_RETENTION_DAYS` | `30` — 최대 이벤트 종료 후 30일. 경품 전달 완료 시 더 일찍 삭제                                 |
| `RULES_VERSION`          | 권장 새 식별자 `app-launch-2026-v4-platform-20261116`. 아래 설명을 검토한 뒤 담당자가 설정      |
| `MAX_SUBMISSIONS`        | 서로 다른 전달 회원번호 수 상한, 기본 1000, 허용 1~10000                                        |
| `MAX_RECEIPTS`           | 기술 접수 이력 상한, 기본·최대 100000. 상한 시 `RECEIPT_CAPACITY_REACHED`로 거절                |

`RULES_VERSION`은 수집 항목의 출처 설명과 접수 계약이 v4로 달라진 것을 구별하기 위해 새 식별자를 권장한다. 이미 저장된 과거 동의 기록을 소급 변경하지 않는다. 현재 운영 속성을 이 문서가 자동으로 바꾸지는 않는다. v4 직접 제출에는 **`EVENT_RELAY_SECRET`이 필요하지 않으며 HMAC 서명을 검사하지 않는다.** 기존 비밀키를 프론트엔드 변수나 Google 제출 본문으로 옮기지 않는다.

`PRIVACY_RETENTION_DAYS`는 **이벤트 종료 후** 최대 보관일수다. 30일은 운영자가 승인한 운영 기준이며 법이 일률적으로 정한 보관기간은 아니다. 경품 전달이 먼저 완료되면 30일을 기다리지 않고 지체 없이 삭제한다. 속성 변경은 자동 삭제 작업을 만들지 않으므로 5절의 삭제 운영을 함께 수행한다.

처리 주체·문의·목적·수집 항목·보관기간은 메타데이터를 통해 응모 폼의 **개인정보 수집·이용 내용 보기**에 표시된다. 동의문에는 다음도 안내한다.

- 수집 항목: 이름, 인스타그램 ID, 브라우저에서 전달한 로그인 회원번호, 응모 시점에 조회하여 전달한 교환글 전체 ID와 개수, 응모 환경(웹·Android 앱·iOS 앱·기기 미확인 앱), 동의 및 접수 기록. 전화번호·사연·사진은 받지 않는다. 응모 환경은 수신부가 해당 기능 지원을 알린 경우에만 전송한다.
- 동의 거부 시 이벤트에 응모할 수 없지만 다른 서비스 기능에는 영향이 없다.
- Google 스프레드시트에 저장하며 처리위탁·국외 이전 사항은 `/privacy`에서 확인할 수 있다. 방침 링크는 입력 중인 폼을 잃지 않도록 새 창으로 연다.
- `RULES_VERSION`은 제출·접수 기록에 남겨 적용한 동의문을 구별한다.

승인 문구·개인정보처리방침·수신부 계약이 서로 일치하는지 확인한 후 공개한다. Google 보관·이전 및 동의 범위도 담당자가 검토하며, 이 문서나 코드만으로 법적 적합성을 보장하지 않는다.

접수 이력 상한에 도달했다고 진행 중 이력을 삭제해 공간을 만들면 과거 UUID 보호가 깨진다. 접수를 중단하고 운영 방식을 조정한다. 정책·일정 변경 시 이미 접수된 동의와 삭제 예정일도 함께 검토한다. 빈 정책·잘못된 일정·미설정 저장소는 접수를 거절하며, 유효하지 않은 메타데이터를 받은 프론트엔드도 폼 활성화를 막는다.

## 3. 기존 웹 앱 업데이트와 DEV 연결

### 연결 순서 — 실제 검증 전에는 접수 닫힘 유지

1. 현재 Apps Script의 `SPREADSHEET_ID`와 완료된 두 탭의 헤더를 확인하고 `ACCEPTING=false`로 둔다. **setup·migrate 함수를 실행하지 않는다.**
2. 같은 프로젝트의 `Code.gs`를 `frontend/scripts/launch-event-apps-script/Code.gs`의 v4 내용으로 교체해 저장한다. 승인한 정책 값과 새 `RULES_VERSION`을 스크립트 속성에 입력한다.
3. **배포 → 배포 관리 → 현재 웹 앱 선택 → 수정(연필) → 버전: 새 버전 → 배포**로 업데이트한다. 이 방식은 기존 배포의 `/exec` URL을 유지한다. 편집기 저장만으로 공개된 웹 앱 코드가 바뀌지는 않는다.
4. 웹 앱은 관리 계정 권한으로 실행하고, 가치가챠 사용자가 별도 Google 로그인 없이 호출할 수 있는 접근 범위로 배포한다. 이는 **접수 URL이 공개된다는 뜻이지 스프레드시트를 공개 공유한다는 뜻이 아니다.** 조직 정책이 허용하지 않으면 담당자와 해결하며 인증을 우회하지 않는다.
5. `/exec` GET 응답이 JSON이며 `schemaVersion: 4`, `authentication: 'client-reported'`, 올바른 이벤트·일정·정책, `accepting:false`를 반환하는지 확인한다. `/dev`, 시트 공유 주소, Google 로그인 HTML은 연결 주소로 쓰지 않는다. 별도로 남은 옛 웹 앱 배포는 사용 여부를 확인한 뒤 보관 처리하여 서로 다른 계약으로 같은 시트에 쓰지 않게 한다.
6. GitHub **frontend-development**의 `EVENT_APPLICATION_ENDPOINT`가 이 `/exec` URL이면 유지한다. 다른 URL이나 `/event-api/launch-event`이면 실제 `/exec` URL로 변경한다. 아래 배너·일정 변수도 맞추고 **변경 코드를 포함한 DEV를 빌드·배포**한다.
7. 먼저 배너·비로그인 비활성 버튼·로그인 후 폼·닫힌 접수 화면을 확인한다. 별도 DEV 테스트 시트·테스트 계정으로 종단 간 검증할 준비가 되었을 때 담당자가 `ACCEPTING=true`로 전환한다. 브라우저와 시트 양쪽에서 성공을 확인하며, 실패하거나 중단하면 다시 닫는다.

GET 메타데이터가 보이는 것만으로 실제 POST·저장·응답 읽기까지 성공한다고 단정하지 않는다. **Google 리다이렉트·CORS·권한을 실제 브라우저에서 확인해야 한다.** EC2 중계 서버, Nginx 경로 추가, 서버 비밀키 배치는 이번 연결 절차에 없다.

```text
EVENT_APPLICATION_CAMPAIGN_ID=app-launch-2026
EVENT_APPLICATION_ENDPOINT=https://script.google.com/macros/s/배포ID/exec
EVENT_APPLICATION_BANNER_START_AT=2026-11-16T00:00:00+09:00
EVENT_APPLICATION_START_AT=2026-11-10T00:00:00+09:00
EVENT_APPLICATION_END_AT=2026-11-28T00:00:00+09:00
EVENT_APPLICATION_ENABLED=true
```

GitHub 경로: 저장소 → Settings → Environments → **frontend-development** → Environment variables. 운영은 별도 **frontend-production**이며 이번 변경 대상이 아니다. `/exec` URL은 브라우저에 노출되는 공개 접수 주소이므로 비밀 인증 수단으로 취급하지 않는다. 배너만 미리 볼 때 endpoint를 비워두면 실제 폼은 열리지 않는다.

**GitHub 변수 저장만으로 이미 배포된 화면이 바뀌지는 않는다.** Webpack이 빌드 때 값을 주입하므로 변경 후 해당 환경을 다시 빌드·배포한다. 최신 배포 대상 커밋을 선택해야 하며 오래된 실행을 재실행하면 코드도 과거 버전으로 배포할 수 있다. 웹 및 같은 원격 웹 주소를 여는 WebView는 새 페이지를 로드하면 적용된다. 이미 열린 앱 화면은 새로고침/재진입이 필요할 수 있다. 웹 콘텐츠 변경만으로 네이티브 재빌드가 필요하지는 않지만 앱 심사·네이티브 변경과는 별개다.

설정된 종료 시각에는 추가 배포 없이 배너가 숨겨진다. 열린 화면은 약 30초 간격 및 화면 복귀 때 재검사한다. 사용자가 기기 시계를 조작할 수 있으므로 접수 마감은 Apps Script의 서버 시각으로도 강제한다.

응모 시작·종료 시각을 바꿀 때는 GitHub 변수와 Apps Script `START_AT`/`END_AT`를 함께 맞춘다. 일정이 다르면 폼을 열지 않는다. 긴급 접수 중단은 **Apps Script `ACCEPTING=false`**로 적용하며 기존에 열린 폼의 신규 접수도 서버가 거절한다. 배너까지 즉시 원격 제어하는 기능은 아니므로 배너 설정 변경에는 다시 빌드·배포가 필요하다.

### 로컬에서 확인할 때

브라우저용 `.env`에 **DEV 테스트 수신부의 `/exec` URL**을 넣고 프론트엔드를 실행한다. 기존 로그인·`/api` 개발 프록시는 유지하며, 별도 이벤트 중계 프로세스는 실행하지 않는다. `.env` 변경 후 개발 서버를 다시 시작한다. 운영 계정·운영 시트로 임의 테스트하지 않는다.

로컬에서도 Google 요청은 같은 직접 제출 계약을 따른다. 로컬 GET 성공이나 테스트 대역의 성공이 DEV·Android WebView·iOS WebView의 CORS와 실제 저장 성공을 보장하지 않는다.

### 실제 접수를 열기 전 필수 검증

- 별도 DEV 프로젝트/시트에서 테스트 계정으로 검증한다. 공개 공유 없이 관리 계정 권한으로 쓰기가 가능한지 확인한다.
- 비로그인 상태에서는 로그인 안내와 비활성 버튼을 보여주고 웹 로그인 화면으로 강제 이동하지 않는지 확인한다. 기존 앱/사이트 로그인 후 돌아오면 폼을 열 수 있고 자동 제출하지 않아야 한다. 입력 중 계정 변경·만료·조회 실패도 점검한다.
- Android WebView/Chrome, iOS WebView/Safari에서 메타데이터 GET·최종 POST·응답 JSON 읽기·완료 화면을 확인한다. Network에서 실제 요청 주소와 리다이렉트를 확인하되 개인정보·인증정보를 공유하지 않는다.
- Google 요청에 `Authorization`, 토큰 본문·쿼리, 쿠키가 없는지 확인한다. CORS 오류가 나면 `mode:'no-cors'`로 우회하지 않고 배포 권한·응답·리다이렉트부터 확인한다.
- 이름·인스타그램·회원번호·모든 페이지의 글 ID·동의 버전이 정확한 열에 저장되는지 확인한다. `@`와 대소문자 정규화도 확인한다. 새 수신부에서는 `운영검증상태`의 웹/Android/iOS 구분과 `참여 조건 확인 필요` 안내를 확인한다. 구버전 수신부/클라이언트는 기존 문구를 유지한다.
- 같은 전달 회원번호로 글 추가 후 재응모하면 새 행이 아니라 최신 1행으로 갱신되는지 확인한다. **이 검사는 회원번호가 서버에서 인증됐다는 증거가 아니다.** 임의 요청의 위조·타인 응모 덮어쓰기 가능성은 운영자가 인지하고 관리한다.
- 같은 UUID·같은 내용 재시도는 한 행과 같은 영수증을 반환하고, 같은 UUID·다른 내용은 거절하는지 확인한다. 과거 요청이 최신 응모를 덮어쓰지 않아야 한다.
- HTML 로그인 페이지·빈 응답·잘못된 캠페인·마감·동의 누락·정책 버전 변경은 완료 화면으로 넘어가지 않아야 한다.
- 실패·시간 초과 시 입력을 유지하고 완료 화면으로 넘어가지 않아야 한다. 서버에 저장됐지만 응답만 못 받은 경우도 있으므로 시트와 접수ID를 대조하며, 충돌을 성공으로 바꾸거나 기록을 지워 우회하지 않는다.
- 마감 직전 부분 저장은 두 탭을 담당자가 대조한다. GAS의 기존 동일 요청 확인·복구 경로와 일반 웹 폼의 마감 차단은 별개이며, 사용자에게 마감 후 재시도를 약속하지 않는다.
- 검증을 통과한 DEV 연결만 활성화한다. 운영 저장소·운영 GitHub 설정 변경은 별도 승인과 검증 후 수행한다.

공개 Apps Script에는 누구나 직접 요청할 수 있다. UUID·요청해시·최대 행수·문자 길이 검사는 회원 인증, 봇 방지, 회원별 요청 제한을 대신하지 않는다. 공격·할당량 부족·의심 접수 발견 시 먼저 `ACCEPTING=false`로 닫고 운영 방식을 점검한다. 오류 로그에 요청 본문·이름·인스타그램·토큰을 추가하지 않는다.

### 연결을 위해 전달할 것

- 기존 배포를 새 버전으로 업데이트한 **`/exec` URL**. `/dev` 또는 시트 공유 URL이 아니다.
- 적용한 동의문 버전·시작/종료 시각 및 `ACCEPTING` 상태.
- GET 응답의 `schemaVersion: 4`, `authentication: 'client-reported'` 확인 결과.
- 액세스 토큰, Google 로그인 정보, 비밀키, 실제 응모자 명단은 전달하지 않는다. 스프레드시트를 공개 공유할 필요도 없다.

## 4. 브라우저 → Apps Script 전송 계약

- 주소: `https://script.google.com/macros/s/배포ID/exec`. 메타데이터 GET과 최종 POST에 같은 웹 앱 URL을 사용한다.
- 일반 `fetch`를 사용한다. POST의 `Content-Type`은 **`text/plain;charset=UTF-8`**, 본문은 JSON 문자열이다. `credentials:'omit'`, `redirect:'follow'`로 Google 쿠키 전송을 피하고 결과 리다이렉트를 따른다. `Authorization` 헤더를 붙이지 않는다.
- **`mode:'no-cors'`를 사용하지 않는다.** 불투명 응답은 접수 결과를 읽을 수 없으므로 전송 호출이 끝났다는 이유로 성공 화면을 보여서는 안 된다. `text/plain` 사용도 모든 환경에서 CORS가 성공한다는 보장은 아니다.
- 허용 필드: `eventId, schemaVersion, submissionId, memberId, name, instagramId, tradeIds, privacyConsent, rulesConsent, rulesVersion`. 새 수신부는 선택 필드 `participationPlatform`(`web|android|ios|app-unknown`)도 허용한다. 지원 capability가 있을 때만 웹에서 보낸다.
- `schemaVersion`은 `4`다. `authentication:'client-reported'`는 GET 메타데이터 값이며 POST 본문에 추가하지 않는다.
- `memberId`와 `tradeIds`는 브라우저에서 구성한 값이다. GAS는 회원 API를 다시 호출하거나 토큰·서명을 검증하지 않는다.
- GAS는 캠페인·버전·동의·정책 버전·접수기간·문자 길이·UUID·중복 없는 양의 정수 글 ID 및 256KiB 본문 상한을 검사한다. 이는 **값의 형식 검사이지 회원·글 소유권 인증이 아니다.**

성공 응답 예시:

```json
{
  "ok": true,
  "eventId": "app-launch-2026",
  "submissionId": "019ab251-394e-4a77-9c21-1221ea123456",
  "receivedAt": "2026-11-16T00:00:00.000Z"
}
```

`ok`만 있는 기존 응답은 성공으로 인정하지 않는다. 응답의 접수ID·이벤트ID·시각을 확인한 후 완료 화면을 표시한다. 영수증은 **전달된 내용을 접수했다는 결과**이며 회원 인증·앱 설치·전체 참여 자격·당첨 확인은 아니다.

Apps Script는 잠금 안에서 접수이력을 먼저 기록한 다음 최신 응모 행을 갱신한다. 같은 UUID·같은 전체 내용은 같은 영수증을 반환하고 다른 내용이면 충돌로 거절한다. 과거 UUID 재시도가 더 최신 응모를 덮어쓰지 않게 한다. 새 UUID와 같은 전달 회원번호로 제출하면 최신 행을 갱신하므로 이 장치가 타인 명의의 새 요청을 막지는 않는다. 두 탭은 데이터베이스 트랜잭션이 아니며 부분 실패가 반복되면 접수를 닫고 담당자가 대조한다.

GAS 내부에는 중단·마감·정책 변경 후에도 기존 UUID와 원래 해시가 같으면 원래 보관기한 안에서 확인·복구하는 경로가 있다. 다만 일반 웹 폼은 접수 가능 여부를 먼저 검사한다. 이 내부 장치를 근거로 사용자에게 마감 후 재시도를 약속하거나 접수를 임의 재개하지 않는다.

## 5. 보관기간 종료와 정리

1. 접수 종료 시 `ACCEPTING=false`로 닫고 운영 담당자와 삭제 확인 일정을 기록한다.
2. 경품 전달 완료 후에는 **최대 30일을 기다리지 않는다.** 담당자가 대상 이벤트를 확인하고 응모정보와 연결된 접수이력을 함께 조기 삭제한다. 현재 코드에는 경품 전달 완료를 감지하는 기능이나 조기 삭제 자동화가 없다. 전체 시트나 다른 이벤트 자료를 일괄 삭제하지 않는다.
3. 최대 보관기한 확인에는 `cleanupExpiredEntries()`를 실행한다. 인자를 생략하면 만료 대상 **개수만** 반환한다. 이 함수는 `삭제예정일`이 지난 행만 찾으므로 2번의 조기 삭제를 대신하지 못한다.
4. 담당자가 보관 기준과 대상 수를 확인한 뒤 `cleanupExpiredEntries(false)`를 실행한다. 이벤트 종료 후 보관기한이 지난 해당 이벤트의 응모 행과 접수이력만 삭제한다. 접수 기간 중 이력은 삭제하지 않는다.
5. 시트 버전 기록, 다운로드한 CSV·복사본 등 잔존 자료도 승인된 보관 정책에 따라 정리한다. 행 삭제는 모든 사본의 영구 삭제를 보장하지 않는다.
6. 저장소 오류가 발견되면 출처를 확인하기 전에 광범위 삭제나 재실행으로 우회하지 않는다.

`PRIVACY_RETENTION_DAYS=30`을 저장해도 자동 삭제 트리거가 설치되지는 않는다. 운영자는 조기 삭제·최대 보관기한 일정을 등록하고 실행 결과를 확인해야 한다. 마지막에는 웹 앱 배포 중지·접근 권한 회수 및 필요하지 않은 보관 사본을 점검한다.

## 로컬 검증

```bash
cd frontend
pnpm exec jest --runInBand src/features/launchEvent src/routes/launchEvent
node --test scripts/launch-event-apps-script/Code.test.mjs
```

이 테스트는 입력·기간·직접 제출 계약·로그인 화면 흐름·중복 접수·시트 수식 방어 등을 모의 환경에서 검증한다. 실제 명령이 성공한 결과만 따로 기록한다. 회원·글 소유권의 서버 인증, Google 권한·쿼터·리다이렉트·실제 브라우저 CORS, 실제 인증 API부터 시트까지의 종단 간 접수, 법적 적합성을 검증한 것으로 기록하지 않는다.

# 가치가챠 Sentry 최적화 원칙

이 문서는 사용자 제공 자료인 「선제적 장애 대응을 위한 Sentry 최적화 적용기」(조호정·황창재·이재희·추용혁, 2025-04-08)의 핵심 교훈을 가치가챠 프론트엔드의 규모·개인정보 정책·현재 구현에 맞게 재해석한 운영 기준이다. 원문 사례를 그대로 복제하지 않고, 현재 저장소와 실제 이벤트 증거를 우선한다.

## 목표

Sentry의 목적은 오류를 최대한 많이 쌓는 것이 아니다. 사용자가 겪는 장애를 팀이 먼저 발견하고, 원인을 재현할 만한 정보가 있는 이벤트를 놓치지 않는 것이다.

- 조치 가능한 오류의 비율을 높인다.
- 동일 원인의 이벤트는 안정적으로 묶고, 다른 원인은 구분한다.
- 노이즈와 rate limit 때문에 중요한 이벤트가 유실되지 않게 한다.
- 알림 피로 없이 실제 장애를 빠르게 인지한다.
- 담당자·검토 상태·결과가 남는 지속 가능한 절차를 운영한다.

## 수집 여부 판단

| 분류 | 기본 결정 | 예시 |
| --- | --- | --- |
| 미처리·예상 밖 실패 | 수집 | 렌더링 중단, 파싱 실패, 핵심 흐름의 예기치 않은 예외 |
| 의도적으로 처리된 사용자 상태 | 제외 | 입력 검증, 정상적인 세션 만료, 사용자에게 안내된 제한 |
| 복구 가능하지만 반복 시 영향이 큰 실패 | `warning`으로 제한 수집 | 특정 브라우저에서 반복되는 일시적 실패 |
| 기능 전체를 막는 실패 | `fatal` 또는 `error`로 수집 | 초기 화면 진입·로그인·검색·상세 진입 불가 |

HTTP 400·401·404 같은 상태코드만 보고 일괄 제외하지 않는다. 같은 상태코드도 엔드포인트와 사용자 흐름에 따라 장애일 수 있다. 제외 전 다음을 모두 확인한다.

1. 해당 조건이 제품에서 의도된 상태인가?
2. 사용자에게 적절한 안내와 복구 경로가 제공되는가?
3. 같은 오류가 급증해도 별도 지표로 탐지 가능한가?
4. 제외 이유와 재검토 시점을 설명할 수 있는가?

네트워크 오류도 브라우저 문구만으로 일괄 제외하지 않는다. `Failed to fetch`, Safari의 `Load failed`, timeout은 사용자 네트워크·CORS·배포 자산·서버 장애를 모두 포함할 수 있다. 우선 환경과 기능 단위로 관찰한 뒤, 비즈니스 흐름에서 안전하게 복구되고 다른 감시 수단이 있을 때만 좁은 조건으로 제외한다.

## 이벤트 정보 고도화

### 허용하는 정보

- `environment`, Git SHA 기반 `release`
- query와 hash가 제거된 route template
- `feature`, `operation`, `error.handled`
- HTTP method, status class, 정규화된 endpoint template이 필요한 경우의 제한된 분류값
- 브라우저·OS·기기 등 Sentry가 개인정보 없이 제공하는 실행 환경
- 로그인 사용자의 숫자형 내부 `memberId`
- 복구 가능 여부와 사용자 영향 등 낮은 카디널리티의 열거형 값

### 금지하는 정보

- 실제 URL query/hash와 OAuth code/state
- access/refresh token, Authorization, Cookie, 비밀번호와 자격 증명
- 요청·응답 body와 header
- 이름, 닉네임, 이메일, 전화번호, 주소
- 채팅, 문의, 댓글, 게시글 등 사용자 작성 본문
- 원본 검색어, 자유 입력 텍스트, 임의의 외부 식별자

원문은 API 응답·헤더·query를 Context로 넣는 사례를 소개하지만 가치가챠에서는 개인정보처리방침과 기존 마스킹 정책 때문에 적용하지 않는다. 필요한 경우 원문 값이 아니라 사전에 정의된 분류값만 남긴다.

## 제목과 그룹화

- 제목은 사람이 첫눈에 기능과 실패 종류를 알아볼 수 있게 한다.
- 동적 ID와 query를 제거한 endpoint template을 사용한다.
- fingerprint는 `오류 분류 + 기능/작업 + 정규화된 endpoint`처럼 안정적인 값으로 구성한다.
- raw URL, 사용자 ID, timestamp, 외부 메시지처럼 매번 달라지는 값은 fingerprint에 넣지 않는다.
- 서로 다른 원인을 억지로 합치지 말고, 같은 원인을 우연히 여러 issue로 쪼개지 않게 실제 이벤트로 검증한다.

## 필터링 순서

가장 가까운 위치에서 의도를 설명할 수 있는 방식을 우선한다.

1. **조건부 capture**: 호출 지점에서 정상 처리 여부를 가장 잘 알 때 수집하지 않는다.
2. **SDK `beforeSend`**: 여러 기능에 공통인 구조적 조건과 개인정보 제거에 사용한다.
3. **Sentry Inbound Filters**: 배포 전 긴급 차단이나 안정적으로 식별되는 문자열 노이즈에만 사용한다.

필터마다 다음을 문서 또는 코드 주석에 남긴다.

- 제외하는 정확한 조건
- 사용자 흐름에서 안전한 이유
- 대신 관찰할 지표가 있는지
- 적용자와 적용일
- 재검토 날짜 또는 제거 조건

필터 적용 후 Sentry의 dropped/rate-limited 수치와 실제 장애 탐지 여부를 함께 본다. 사용량 감소만으로 성공이라 판단하지 않는다.

## 알림 기준

- `production`만 실시간 알림 대상으로 삼는다.
- 신규 `fatal`/critical 성격 오류는 즉시 확인한다.
- 동일 issue가 10분 안에 5회 이상 발생하면 반복 장애 후보로 알린다.
- `development`는 수동 확인 또는 일일 요약을 사용한다.
- 첫 설정부터 모든 신규 issue를 알리지 않는다. 실제 사건을 검토하며 threshold를 조정한다.
- 무료 플랜이나 기능 제한으로 원하는 규칙을 만들 수 없다면, 가장 중요한 P0/P1 규칙부터 유지한다.

## 운영 절차

1. 담당자를 최소 2명 묶어 일정 기간 교대로 지정한다.
2. 알림을 본 담당자는 스레드나 이슈에 확인 중임을 표시한다.
3. environment, release, first/last seen, 횟수, 영향 사용자, route, 브라우저·OS, 원본 stack을 확인한다.
4. 필요한 경우 member ID와 시각으로 PostHog 세션을 교차 확인한다.
5. 결과를 `재현됨`, `수정 예정`, `의도된 처리`, `정보 부족`, `노이즈 필터 후보` 중 하나로 기록한다.
6. 검토 완료 표시와 담당자·시각을 남겨 중복 조사를 막는다.
7. 매주 상위 빈도 issue, 새 필터, rate limit, 미처리 P1 이상을 짧게 점검한다.
